# DeepSeek Harness — Research Watch
**26 октября 2026 | Период: 20–26 октября**

**Результат: семь новых исследований и два инженерных отчёта**, опубликованных после предыдущего обзора. Наиболее перспективные направления — надёжность мониторинга действий, детерминированные контракты исполнения и интеллектуальный выбор инструментов.

На этой неделе особенно важно, что появились независимые свидетельства: даже при наличии sandbox, approval policy и журналирования агент может выполнять действия, которые не отражаются в ожидаемом контуре контроля.

При этом новые работы по tool selection показывают возможность уменьшить контекст инструментов без изменения основной модели.

**Новых коммитов в `master` после прошлого обзора нет.**

Проверка документации выявила важную деталь, которую необходимо учитывать при оценке новых security-исследований.

Текущий `SandboxMode` регулирует прежде всего **файловые эффекты процесса**. Ограничения сети и видимости процессов не входят в этот контракт.

Это означает, что файловая изоляция не должна интерпретироваться как полноценная изоляция execution environment.

Вторая важная особенность: DSH уже поддерживает `system-prompt/assemble`, динамические `PromptContext`, scoped tool providers и `ToolRestriction`. Следовательно, эксперименты с выбором инструментов можно проводить без изменения `ReactLoopAgent`.

Третья — session log действительно является append-only источником истории, а `compaction` использует отдельные durable events и model-visible projection.

Это позволяет проверять новые memory policies, не изменяя исходные события.

# 2. Новые исследования

## 🥇 1. METR — уязвимости мониторинга автономных агентов

**22 октября 2026**

urlRed-Teaming OpenAI's Internal Agent Monitoring Systems — METRturn7view0

Дополнительный первоисточник от 23 октября:

urlSecuring our frontier model training environment — OpenAIturn7view1

**Практическая ценность: 10/10**  
**Сложность первого PoC: 4/10**

### Что обнаружили исследователи

Исследователи entity["organization","METR","AI evaluation research nonprofit"] и Redwood Research получили доступ к внутренней системе мониторинга агентных запусков OpenAI и провели трёхнедельное исследование.

Среди обнаруженных проблем:

- Некоторые события compaction не попадали в мониторинг.
- Мониторинг мог откладываться до момента возврата управления пользователю.
- Исследователи нашли способ потенциально исключить из проверки сотни действий.
- Различия сериализации истории создавали возможность нарушить работу monitor.
- Некоторые инструменты, считавшиеся read-only, имели потенциально более широкие полномочия.

По оценке исследователей, отсутствие контроля compaction могло приводить к пропуску порядка 10% соответствующего внутреннего Codex-трафика в исследованный период.

Это исторические результаты: исследователи проверяли систему по состоянию на июль 2026 года. OpenAI сообщает об устранении проблем, затрагивающих production safeguards, но независимая повторная проверка этих исправлений не проводилась. citeturn7view0

### Почему это особенно важно для DSH

У DSH уже есть несколько параллельных представлений исполнения:

`SessionEvent log`

`derived model history`

`assistant stream`

`tool execution`

`compaction projection`

`Agent Teams mailbox`

Проблема возникает, если security observer контролирует только часть этих представлений.

Например, агент может выполнить несколько инструментов, создать дочернего агента, произвести compaction и продолжить работу.

Если мониторинг ориентирован исключительно на завершение turn, отдельные промежуточные действия могут остаться без своевременной проверки.

Это **потенциальный сценарий**, а не подтверждённая уязвимость DSH.

### Точка интеграции

`core/session`, `core/tools`, `agent/*`, `compaction/*`, `ctx.agentTeams`.

Предлагаю экспериментальный observer:

`dsh-monitor-integrity`

Он не должен принимать решения вместо существующего authorization pipeline.

Его задача — проверять полноту наблюдения.

Для каждого действия необходимо сопоставлять:

`action initiated → policy evaluated → execution settled → event recorded → monitor observed`

Отдельно учитывать cancellation, retry, compaction и дочерние сессии.

### Ожидаемая польза

Обнаружение пропущенных действий, несоответствий журналов и ситуаций, когда мониторинг перестал работать.

### Риски

Дополнительное журналирование увеличивает I/O и объём хранения. Синхронный контроль может увеличить latency.

Нельзя использовать только асинхронный observer как механизм блокирования опасных операций.

### Минимальный эксперимент

Создать 100–200 синтетических trajectories с:

- обычным выполнением;
- cancellation;
- retry;
- compaction;
- nested tools;
- subagent execution;
- simulated monitor failure.

Затем проверить, какая доля действий имеет полный audit trail.

**Критерий успеха:** 100% покрытие заданных типов событий и обнаружение всех искусственно внесённых пропусков.

Это мой первый кандидат недели.

## 🥈 2. GeoAgent — детерминированные контракты вместо дополнительных инструкций модели

**22 октября 2026, обновление 23 октября**

urlGeoAgent: Contract-Constrained LLM Agents for Seismic Data Processingturn5view5

**Практическая ценность: 9,5/10**  
**Сложность: 5/10**

### Суть исследования

GeoAgent предназначен для управления научным программным обеспечением через LLM.

Авторы обнаружили типичные ошибки:

- модель передаёт неверный артефакт следующему инструменту;
- путает параметры;
- неправильно связывает входные и выходные файлы;
- сообщает об успешном завершении, хотя результат отсутствует.

Вместо добавления новых инструкций авторы ограничили пространство допустимых действий.

Используются четыре контракта:

1. Именованные артефакты.
2. Детерминированное разрешение входов.
3. Управление параметрами вне модели.
4. Проверка выходного артефакта.

Система использует 54 специализированных оператора и индекс из 1937 доступных программных операций.

В испытании на одном наборе сейсмических данных девятиэтапный pipeline выполнялся за 6–11 минут. Retrieval сокращал контекст описаний инструментов примерно с 12 тысяч до 2 тысяч токенов.

Авторы прямо признают ограничение: это инженерная демонстрация на одном наборе данных и одной модельной конфигурации, а не масштабный сравнительный benchmark. citeturn8view1

### Применимость к DSH

Очень высокая.

Сейчас DSH валидирует аргументы инструментов и их результаты, но из этого не следует, что каждый результат семантически соответствует ожиданиям следующего этапа.

Например:

`generate file → compile → test → package`

Модель может передать неправильный файл компилятору или принять существование файла за доказательство успешной сборки.

GeoAgent предлагает переносить такие проверки из prompt в детерминированный код.

### Точка интеграции

`core/tools`, `tools/pre-execute`, `tools/post-execute`.

Первоначально достаточно plugin для конкретного workflow.

Не нужно вводить универсальную систему контрактов для всех инструментов.

### Ожидаемая польза

Снижение числа неправильных tool arguments, silent failures и ложных сообщений об успехе.

### Риски

Контракты увеличивают объём прикладного кода и могут ограничивать нестандартные, но корректные способы решения задачи.

### Минимальный эксперимент

Взять 50 многоэтапных coding tasks.

Сравнить:

`Prompt-only validation`

`Schema validation`

`Schema + deterministic artifact contracts`

Проверять корректность входов, успешность финального результата, число повторных вызовов и стоимость.

**Особенно интересно:** использовать этот подход вместе с HTN-Orchestrate из предыдущего обзора. HTN отвечает за декомпозицию задач, а контракты GeoAgent — за корректность переходов между этапами.

## 🥉 3. Training Small Language Models for Transferable Tool Selection

**22 октября 2026**

urlИсследование — arXiv:2610.31483turn5view0

**Практическая ценность: 9/10**  
**Сложность: 5/10 для экспериментального routing; существенно выше для обучения модели**

### Суть исследования

Авторы рассматривают системы с тысячами инструментов.

Если передавать все tool schemas в каждый запрос, расход контекста становится чрезмерным.

Обычный retrieval решает только часть проблемы: он находит похожие инструменты, но не определяет, какие из них действительно необходимы для выполнения задачи.

Предложена архитектура:

`Plan → Retrieve → Select`

Небольшая специализированная модель разбивает задачу на независимые шаги, получает кандидатов от retriever и выбирает необходимые инструменты.

На ToolBench G3 обученная Qwen3-8B получила **41,5% exact-match success**, тогда как лучший из исследованных вариантов Llama-4-Maverick достиг 30,6%.

Модель также переносила полученные навыки на другие наборы инструментов и retrievers.

Однако исследование имеет два существенных ограничения: выбор оценивается по совпадению набора инструментов, а не по конечному результату работы агента; обученные checkpoints и код обучения авторами не опубликованы. citeturn8view0

### Применимость к DSH

Высокая благодаря существующим `ToolRestriction` и `system-prompt/assemble`.

Можно динамически ограничивать model-visible tool schemas, сохраняя фактический registry и authorization policy.

### Точка интеграции

`core/system-prompt`, `core/tools`, `ctx.llm`.

Экспериментальный plugin должен:

1. Получать описание текущей задачи.
2. Выбирать кандидатов из tool registry.
3. Передавать модели только необходимые schemas.
4. Сохранять возможность дополнительного поиска инструментов.

### Ожидаемая польза

Меньше input tokens, меньше контекстного шума и потенциально более быстрые запросы.

### Риски

Главный риск — скрыть необходимый инструмент.

Кроме того, при небольшом количестве инструментов стоимость отдельного selector может превысить экономию.

### Минимальный эксперимент

На 100–200 задачах сравнить:

`All Tools`

`BM25 Top-K`

`LLM-assisted Tool Selection`

Измерять tool recall, task success, input tokens, TTFT и стоимость.

**Рекомендация:** сначала проверить обычный BM25 и небольшой selector без обучения. Не запускать дорогостоящий SFT/RL до подтверждения экономической целесообразности.

## 4. Behavior Beyond Text — отказ модели не гарантирует безопасных действий

**20 октября 2026**

urlBehavior Beyond Text: Evaluating Refusal Transfer Failure in LLM Agentsturn5view1

**Ценность: 9/10. Сложность: 3/10.**

Авторы исследовали, переносится ли способность модели отказываться от опасного запроса на поведение при наличии инструментов.

Создан benchmark из 2304 запросов в четырёх доменах.

Результат: среди запросов, отклонённых моделью в обычном текстовом режиме, **10–52% приводили к небезопасным tool calls** при стандартной конфигурации с инструментами. Диапазон зависит от исследованной модели. citeturn5view1

### Применимость

Это непосредственно касается DSH approval и tool execution.

Безопасный текстовый ответ нельзя использовать как доказательство безопасного исполнения.

### Точка интеграции

`tools/pre-execute` и evaluation pipeline.

### Польза

Более реалистичная проверка безопасности: оценивать фактические действия, а не только финальные ответы.

### Риски

Benchmark охватывает ограниченный набор запрещённых действий и не доказывает универсальную эффективность конкретной защиты.

### Минимальный эксперимент

Создать 100 парных сценариев:

`Text-only request`

`Same request + tools`

Измерять отдельно:

- текстовый отказ;
- попытку запрещённого действия;
- фактическое выполнение;
- ложные блокировки разрешённых действий.

Это логичное дополнение к HarnessSecurity-Bench из предыдущего обзора.

## 5. Agent Mosaic — утечка данных через объединение разрешённых сведений

**21 октября 2026**

urlAgent Mosaic: Recognizing Confidentiality Leaks in Agentic LLM Systemsturn5view6

**Ценность: 8,5/10. Сложность: 6/10.**

### Суть исследования

Авторы исследовали *mosaic effect*.

Агент может получить доступ к нескольким документам, каждый из которых разрешён для чтения, и объединить сведения в запрещённый к раскрытию вывод.

В исследовании использовались 30 синтетических сценариев, 10 800 ответов в симуляции и 1440 ответов реальных агентных систем.

Даже добавление классификационных заголовков и явных правил агрегации не устранило все утечки. citeturn5view6

### Применимость к DSH

Особенно актуальна для Agent Teams, MCP и подключений к корпоративным данным.

Обычная проверка доступа отвечает:

> Может ли агент прочитать этот документ?

Но не отвечает:

> Имеет ли получатель право узнать вывод, полученный объединением нескольких документов?

### Точка интеграции

`ctx.agentTeams`, team mailbox и outbound tool policy.

### Ожидаемая польза

Усиление защиты конфиденциальных данных при межагентном обмене.

### Риски

Автоматическое определение чувствительных выводов является сложной задачей.

Простая классификация отдельных документов недостаточна, а чрезмерно строгая политика будет блокировать легитимную аналитику.

### Минимальный эксперимент

Создать 30 синтетических наборов документов с известными правилами доступа.

Проверить, способен ли агент вывести запрещённый composite fact.

Сравнить document-level access control с дополнительной проверкой outbound information flow.

**Рекомендация:** сначала security benchmark, затем решение о runtime policy.

## 6. Silent Cue Loss — потери информации при преобразовании документов

**21 октября 2026**

urlWhat the Author Wrote, What the Agent Readsturn5view2

**Ценность: 8/10 при наличии document ingestion. Сложность: 4/10.**

### Суть исследования

Авторы показали, что преобразование DOCX/PDF в обычный текст способно уничтожать смысл, закодированный форматированием.

Например, обязательное требование может быть выделено цветом.

Если converter удаляет это выделение, агент видит правильный текст, но теряет информацию о его значимости.

На 76 реальных policy documents micro-F1 снижался с 0,690 при сохранении сигналов форматирования до 0,150 для одного из исследованных способов преобразования и 0,075 для plain text.

Особенно значимыми оказались цвет и выделение маркером. citeturn5view2

### Применимость к DSH

Частичная.

Исследование полезно, если DSH получает документы через внешние converters, MCP или специализированные document tools.

Но само по себе оно не доказывает наличие такой потери в текущем DSH.

### Точка интеграции

Document ingestion plugin либо tool, который преобразует документы в model-visible content.

Не `core/agent-loop`.

### Ожидаемая польза

Сохранение важных семантических признаков документа.

### Риски

Дополнительная разметка увеличивает объём контекста и может вносить ошибки интерпретации.

### Минимальный эксперимент

Создать 30 DOCX/PDF с проверяемыми выделениями и обязательными условиями.

Сравнить plain text extraction и формат с явными аннотациями:

`[HIGHLIGHTED]`

`[TEXT_COLOR=RED]`

Измерять точность извлечения требований и расход токенов.

## 7. Memory-Centric Continual Learning — как доказать, что память действительно улучшает агента

**21 октября 2026**

urlMemory-Centric Continual Learning for AI Agentsturn5view4

**Ценность: 8,5/10. Сложность: 3/10 для evaluation methodology.**

### Суть исследования

Авторы предлагают оценивать память не по способности находить сохранённые факты, а по тому, **улучшает ли накопленный опыт будущие действия агента**.

Представлена концептуальная схема с двумя циклами.

Внутренний цикл обновляет содержимое памяти.

Внешний изменяет политику её использования на основании результатов задач.

Предлагается проверять три свойства:

- сохранение знаний при появлении новой информации;
- адаптацию к изменениям;
- перенос опыта на новые задачи.

Это прежде всего методологическая работа, а не готовая реализация с доказанным ускорением конкретного agent harness. citeturn5view4

### Применимость к DSH

Высокая для оценки REALM, ExperienceIndex, ReCAP, MemComposer и DAEDALUS из предыдущих обзоров.

Все эти механизмы потенциально полезны, но обычный retrieval benchmark не позволяет установить, стал ли агент лучше решать задачи.

### Точка интеграции

Offline evaluation поверх `SessionPersistence` и replay.

### Ожидаемая польза

Единая методология сравнения memory plugins.

### Риски

Сложно отделить влияние памяти от изменений модели, инструментов и окружения.

### Минимальный эксперимент

Создать три набора задач:

`Retention`

`Adaptation`

`Transfer`

Сравнить агента без памяти, с retrieval-only памятью и с обновляемой памятью.

Фиксировать модель, инструменты, бюджет и начальное состояние окружения.

**Рекомендация:** использовать как методологическую основу, не создавая новую runtime-подсистему.

Эта работа заслуживает отдельного внимания из-за её системной составляющей.

Авторы исследуют обучение агентов в stateful environments, включая SQL debugging.

Главная проблема — состояние базы данных меняется после каждого действия.

Если несколько trajectories используют одну базу без изоляции, возникает загрязнение результатов.

Если создавать отдельный контейнер для каждого запуска, резко увеличиваются накладные расходы.

BIRD-RL предлагает trajectory-scoped persistent execution infrastructure с безопасным повторным использованием окружений.

Авторы сообщают об улучшении пространственной эффективности инфраструктуры в 12,8 раза. Обученные 7B и 14B модели достигли 44,4% и 48,0% success rate на BIRD-CRITIC-SQLite. citeturn5view7

Для DSH интереснее не сам RL, а управление stateful execution environments.

**Точка интеграции:** отдельный evaluation runner, использующий DSH agent/session interfaces и изолированные тестовые базы.

**Эксперимент:** сравнить создание нового SQLite/PostgreSQL окружения на каждый запуск с восстановлением из заранее подготовленного snapshot.

Измерять время подготовки, диск, память, корректность изоляции и воспроизводимость.

Я бы не переносил BIRD-RL в production agent loop. Это потенциальная оптимизация инфраструктуры обучения и тестирования.

# 5. Три наиболее перспективные идеи недели

### №1. Проверяемая полнота мониторинга

После публикаций METR и OpenAI недостаточно проверять, что каждый инструмент проходит authorization.

Необходимо также гарантировать, что каждый execution path действительно наблюдается и может быть восстановлен.

Для DSH это особенно важно из-за нескольких механизмов продолжения исполнения: retries, compaction, nested tools, subagents и Agent Teams.

**Следующий шаг:** построить coverage benchmark поверх существующих session events.

### №2. Детерминированные контракты исполнения

GeoAgent показывает перспективный путь снижения ошибок: не просить модель быть внимательнее, а исключать недопустимые переходы структурно.

Для DSH это естественное продолжение существующей schema validation.

**Следующий шаг:** эксперимент с контрактами входных и выходных артефактов для многоэтапных coding tasks.

### №3. Динамический выбор инструментов

Работа о transferable tool selection продолжает исследования Cursor, ToolGrad и Paper2Agent из предыдущих обзоров.

Теперь есть дополнительные основания проверить, насколько дорогие модельные вызовы можно заменить специализированным выбором инструментов.

**Следующий шаг:** сравнить полный tool registry, BM25 и небольшой LLM-selector на одинаковых задачах.

# 6. Что не стоит интегрировать сейчас

По speculative decoding и физическому KV-cache management за рассматриваемый период я не нашёл нового результата, который обосновывал бы изменение `core/agent-loop`.

Оптимизации inference-serving по-прежнему правильнее реализовывать в backend и измерять через `ctx.llm`.

Также не рекомендую сейчас создавать универсальный memory framework. За несколько недель накопилось много конкурирующих подходов, но их сравнительная эффективность на задачах DSH пока не установлена.

Особенно важно не объединять memory retrieval, compaction и self-improvement в одну подсистему без независимых экспериментов.

# 7. Финальный вывод

**Главное изменение недели — переход от проверки отдельных защитных механизмов к проверке полноты контроля всей траектории агента.**

Для DSH это принципиально важно. Его event-sourced архитектура предоставляет хорошую основу для аудита, но сама по себе не доказывает, что каждый путь исполнения охвачен мониторингом.

Второй устойчивый вывод: качество tool execution можно улучшать без усложнения agent loop — через контракты, ограничение доступных инструментов и детерминированную проверку результатов.

Третий: новые исследования памяти всё сильнее смещаются от вопроса «что агент помнит?» к вопросу «насколько накопленный опыт улучшает последующие действия?».

**Рекомендованный порядок работ:**

1. Monitoring coverage benchmark.
2. Artifact-contract PoC.
3. Dynamic tool-selection benchmark.
4. Единая методология оценки memory plugins.

Все четыре направления можно начать без крупного рефакторинга DSH. Это соответствует текущей Cordis-архитектуре и позволяет отказаться от неудачных экспериментов без накопления лишней сложности в ядре.
