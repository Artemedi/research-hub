### Вывод для DSH

Грааля нет. Результаты асимптотические, константы галактические (κ = 2⁻¹⁸², δ = 10⁻¹³), угроз классической криптографии нет. Остальные 391 постановку гонять ради DSH не нужно: следующий PASS не скажет больше, а главный риск — верность постановок, а не доказательств.

Для DSH отсюда следует одно: неизменяемая постановка, которую принимает человек, плюс механический проверяльщик с белым списком аксиом. Это и есть схема пунктов 1 и 3 ниже.

## Вывод

Кардинально упростить продукт математикой нельзя: узкое место — доказательство корректности текстом и ревью, а не вычисления. Отдачу дают механические оракулы и априорные границы. Они убирают раунды ревью и STOP-события до запуска.

Решения владельца (governance), авторизация SHA, права Tier R и внешние неизвестные вроде биллинга моделью не заменяются.

## 1. Байт-капы: формула вместо STOP после сборки

Канонический писатель квитанций — `json.dumps(ensure_ascii=True, separators=(',',':'))`. Сколько байт даёт один байт сырого UTF-8 после экранирования:

| Класс | Байт на сырой байт |
|---|---|
| ASCII | 1 |
| `"` и `\` | 2 |
| управляющие символы | 6 |
| 2-байтовый UTF-8 | 3 |
| 3-байтовый UTF-8 | 2 |
| 4-байтовый UTF-8 (суррогатная пара `\uXXXX\uXXXX`) | 3 |

Верхняя граница экранированной строки при сыром размере ≤ R и ASCII-префиксе P: `2 + P + 3·(R − P)`. Если допускаются управляющие символы, множитель 6.

Проверка на свидетеле STOP E517: восемь путей по 280 байт UTF-8.

| Величина | Байт |
|---|---|
| фактический размер | 9918 |
| тот же шаблон с ASCII-путями | 6430 |
| граница по формуле | 9934 (≥ 9918 → STOP предсказуем) |
| худший случай без префикса | 10910 |

Под кап 8192 при восьми полностью не-ASCII путях помещается ≤ 166 сырых байт на путь. Правило E518 («экранированная строка ≤ 282 байт») — частный случай этой формулы.

**Применение:** любой новый кап проверять формулой до сборки прототипа. Асимптотику размера (квадратичные копии вложенных путей) — тоже до ревью.

## 2. Статистика стенда: n выбирается под утверждение заранее

Ноль срабатываний из n прогонов. Точная 95%-верхняя граница Клоппера–Пирсона: `1 − 0.05^(1/n)`.

| n | 5 | 25 | 26 | 60 | 100 | 300 |
|---|---|---|---|---|---|---|
| граница, % | 45.1 | 11.3 | 10.9 | 4.9 | 2.95 | 0.99 |

- Для границы ≤ 10% нужно 29 прогонов, для ≤ 5% — 59, для ≤ 1% — 299.
- Максимум выборки — 95/95-верхняя граница для p95 только при n ≥ 59. При n = 25 уверенность 72%. Нормальность не нужна.
- Следствие для пятипутевого стенда: 25 POST на пять путей дают границу ~45% на путь. До замера нужно зафиксировать, какое утверждение покупается, иначе числа снова будут UNQUALIFIED.

## 3. Механический оракул «нет await между guard и commit»

- Проверка по синтаксическому дереву TypeScript (`typescript` из `node_modules` Runtime): в `admit()` (`packages/host-adapter/harness/invocation.ts`) ищутся `await`, `yield` и `for await` после `await Promise.race` и до return коммита. Вложенные функции пропускаются.
- На `95d75697`: одна гонка (стр. 174), коммит на стр. 222, 0 нарушений.
- Оба подставленных мутанта пойманы: `await` перед D_PRE-проверкой и `await` на handoff.
- Работает доли секунды. Это кандидат в `qualify` вместо подтверждения ревьюером по тексту.

## 4. Точность таймеров Node и D_PRE/D_POST

- Node v22.23.2: `setTimeout(d)` в ~0.9% вызовов срабатывает раньше, чем `performance.now()` продвинется на d. Максимальное опережение — 0.99 мс (замер на 3000 вызовах).
- В `invocation.ts` истечение D_PRE определено дважды: таймером в гонке со свежестью и проверкой `performance.now() − acceptedAt ≥ preCommitMs` на guard. Определения расходятся на ≤ 1 мс: DEADLINE_REFUSED возможен на отрезке [D − 1 мс, D). Флаг D_POST — так же.
- Перебор 22 692 трасс на виртуальных часах:
  - abort важнее истечения (P1) — 0 нарушений;
  - коммит только при elapsed < D (P2) — 0 нарушений;
  - «отказ только при elapsed ≥ D» (P3) нарушается только из-за опережения таймера.
- По тексту DL V2 («races a timer set to the remaining D_PRE») это, вероятно, допустимо. Кандидат в residual для нормативного ревью, не блокер.
- В `phase2d-deadlines.spec.ts` нет утверждений о точном времени, флейков отсюда нет.

**Применение:** не утверждать порядок событий с точностью до миллисекунды на реальных таймерах. Для тестов дедлайнов — инжектируемые часы и ручные таймеры вместо `sleep` и busy-wait.

## 6. Память и перенос памяти

- **Milestone 7 (recall):**
  - качество — стандартными метриками поиска (recall@k, MRR, nDCG) против базы BM25 / усечения; это то же условие, что для REVA в `docs/research-assimilation-plan.md`;
  - упаковка в байтовый бюджет — задача о рюкзаке: жадный отбор по score/byte даёт 1/2-приближение;
  - дубликаты — MMR.
- **bitvec (решения там принимает владелец через NEXT.md):**
  - Phase 1 inconclusive: CE R-text 1.81, G-bridge 2.88, G-bridge+text 1.87, G-random 4.25;
  - shuffle-диагностика: выигрыш в основном не зависит от промпта;
  - soft-prefix не несёт о промпте больше, чем сам текст (data-processing inequality), поэтому для продукта DSH текстовая память (TencentDB + evidence boundary) достаточна, мост остаётся исследованием вне критического пути;
  - дешёвый следующий шаг: закрытая форма (ridge / ортогональный Прокруст) по уже извлечённому кэшу как база, выбор слоя по CKA вместо ручного `reader_layer_idx: 18`.
