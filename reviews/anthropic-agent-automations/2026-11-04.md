## Метод и ограничение гарантии

Scheduled brief читает источники с отдельными bookmarks, перекрывает 10 минут, использует ledger для дедупликации, повторно проверяет актуальность, сообщает о сбоях чтения и не двигает bookmark неуспешного источника. Перед записью проверяется название сегодняшнего выпуска; запись считается подтверждённой при `ok: true` и `ts`, при неизвестном результате сохраняется `maybe posted`, а исходные bookmarks не двигаются. Preferences и state разделены с разными правами; GitHub token задуман read-only, Slack token имеет доступ на чтение и публикацию, сеть ограничена по хосту, web tools отключены. В примере задан ceiling бюджета на запуск. Dry-run достигается read-only state, что по инструкции должно отключать публикацию.

Это **проектный протокол и инструкции агенту**: доказательства атомарной транзакции между Slack и memory store, распределённой блокировки или строгой идемпотентности в примере не установлены. Проверка наличия заголовка перед отправкой может гоняться с другим запуском и зависит от доступности/полноты истории; `maybe posted` не устраняет автоматически неоднозначный результат. Не утверждаем, что эти риски реально проявились на Claude Managed Agents. Prompt injection может повлиять на сформированный текст даже при ограничении действий, что авторы отдельно признают.

Предыдущий [LIMBO × TelegramBot lab](../exactly-once-limbo/2026-11-04.md) показал на искусственных сервисных сценариях различие timeout до и после эффекта и риск blind retry. Его 180 synthetic trajectories относятся к другому инструменту, **не** измеряют частоту или реализацию Slack/Anthropic. Запуск reference, платных моделей, API и внешняя отправка `NOT_RUN`.
