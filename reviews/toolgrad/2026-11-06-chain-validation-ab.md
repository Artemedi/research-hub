## Метод и изоляция

[Воспроизводимый тест](../../experiments/2026-11-06-bk005-toolgrad-chain-validation-ab.py), [полный JSON, 500 цепочек и отрицательные контроли](../../data/results/toolgrad/2026-11-06-chain-validation-ab.json). 5 независимых seeds `20261106–20261110` × 100 заданий; 12 безопасных инструментов полностью в памяти (`create, owner, note, priority, tag, evidence, ack, validate, snapshot, close, reopen, report`). Длины успешных цепочек — **2–6**, независимый oracle — изменения множества состояний и предусловия переходов. SQL, файловые операции на реальном проекте, внешний транспорт и производственные процессы не вызывались.

**A: answer-first proxy.** Детерминированный proposer выбирает только действия с удовлетворёнными предусловиями. Каждый результат пропускается через **настоящий** авторский `validate_api_response`; запись шагов в Pydantic workflow выполняет **настоящий** `chain_update_step`, проверяется содержимое action history. Только после исполнения строится шаблонный текст задания. Авторские Gemini proposer, tool-calling executor, LLM selector и inverse predictor **не исполнялись** — подменены детерминированной логикой исследования.

**B: query-first bounded DFS proxy.** Наш алгоритм получает тот же уже **достижимый** конечный goal, но без исходной цепочки. Ищет допустимые действия при ограничениях 80 и 400 посещённых состояний, случайный фиксированный порядок обхода для каждого seed/задания, одинаковые tool preconditions и отдельный state oracle. Это **не** авторский ToolBench DFS / LLM-agent, поэтому их стоимость, возможность рассуждения и ошибки отсутствуют. Выбор целей из A облегчает обеим веткам работу (все запросы заведомо разрешимы); у B при проверке каждого инструмента учитываются также неудачные попытки, тогда как A знает допустимые действия заранее. **Это не строго feature-equal comparison.**

Ресурсы Bazzite, Python 3.14.8, `uv sync --frozen --no-dev --no-install-project` в одноразовом каталоге, `env -i` с фиктивным HOME и отключением записи bytecode. Истинные ключи моделей не были доступны тестовому процессу, модельные API не вызывались. На стадии установления зависимостей `uv` использовал публичный пакетный индекс; сама исследовательская программа выполняла только локальные функции и не содержала сетевого транспорта. В оригинальном `src/models/model_lib_test.py` находится **живой** запрос к LLM; этот файл сознательно не запускался.

## Непосредственно измеренное

| Показатель | Answer-first A, оригинальный chain updater | Query-first B, наш DFS, лимит 80 |
| --- | ---: | ---: |
| Успешно достигнуты проверяемые конечные состояния | **500/500** | **500/500** |
| Синтетических шагов: mean / p50 / p95 | 4,308 / 5 / 6 | 4,308 / 5 / 6 успешных переходов |
| Все попытки вызова инструментов | 4,308 успешных / задачу | **27,924** попытки / задачу, включая отказы preconditions |
| wall p50 / p95 на задачу | 0,384 / 0,621 ms | 0,071 / 0,117 ms |
| Независимая корректность состояния | 500/500 | 500/500 |

При лимите **400** DFS также **500/500**, среднее 28,178 попыток, p50 wall 0,070 ms / p95 0,115 ms. По 500 наборам задействованы **все 12** названных инструментов, в том числе редко достижимый `reopen` — **50 раз**. На такой малой, монотонной области B не потребовалось даже 80 узлов поиска; источник `chain-first` здесь не дал прироста correctness. Считать отношение времени 0,384/0,071 показателем сравнительной эффективности алгоритмов **нельзя**: A создаёт LangChain+Pydantic объекты, B — чистый Python, модельные вызовы отсутствуют.

**Отрицательные контроли:** 500/500 укороченных на последний шаг цепочек дали несовпадающее конечное состояние и были отклонены oracle. 100/100 отдельно заданных невозможных goals `create ∧ reopen ∧ ¬close` отклонены DFS. Заведомо неверная метка запроса также не совпала с oracle (ошибка значения выявлена). Это проверка именно нашем фиктивном DSL, не внешних API.

## Существенный результат по оригинальному validator

Отдельно вызвана реальная `module_lib.validate_api_response` на 50 фиксированных ответах; независимый expected label задавался самим безопасным тестовым контрактом.

| Класс ответа | Expected accepted | Actual accepted | Вывод |
| --- | ---: | ---: | --- |
| 10 корректных непустых JSON | 10 | 10 | PASS |
| 10 корректных JSON с `error_count: 0` | **10** | **0** | **10 false negatives** |
| 10 `ok=false, error=denied` | 0 | 0 | PASS |
| 10 пустых ответов | 0 | 0 | PASS |
| 10 response с transport exception | 0 | 0 | PASS |

Причина **в текущей исходной эвристике**, а не в реальном сервисе: `_contains_error_keywords` проверяет вхождение `error` как подстроки, поэтому невинное поле `error_count` создаёт ложную тревогу. Обратная проблема: `{"ok":true,"revision":1}` проходит source validator, даже если фальшивый сервис **вообще не изменил состояние**; только наш независимый oracle обнаруживает отсутствие эффекта. Это **два разных ограничения**: наблюдаемая конкретная false-negative ошибка по данным и принципиальная неспособность текстового валидатора доказывать внешний commit. Они не означают, что остальные инструменты ToolGrad неизменно работают неправильно.

Все 500 цепочек использовали иной корректный ответ `{"ok":true,"revision":N,"case_id":"synthetic-only"}`, для которого в этом опыте validator PASS. Поэтому ошибки `error_count` не влияли на результат 500/500, а фиксируются отдельной воспроизводимой регрессией.

## Стоимость и границы

На 500 задачах вся измеряемая Python evaluation loop: **0,325 s wall**, **0,319 s CPU**, `tracemalloc` peak **1 079 037 bytes**; process `ru_maxrss` **400 140 KiB** (суммарное residency процесса с загруженными LangChain/Pydantic и зависимостями, не per-arm) и `/proc/self/io write_bytes` 4096 bytes по accounting всего процесса. Эти числа **не представляют** стоимость модели, provider API, полноту диск IO или типичную latency tool calls. LLM calls 0; inference tokens, USD и VRAM — `N/A`. Рандомизация порядка обхода между seed есть, но генератор и DFS — ручные локальные прокси; сравнение не переносится на 16k API.
