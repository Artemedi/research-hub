## 1. Реализованный механизм — не Docker-compatible runtime

- **VERIFIED — без Docker Engine / LXC userspace:** `rurima pull/docker/lxc` загружает rootfs (Docker registry layer и LXC mirror); `unpack/load` извлекает архивы; `backup/restore` использует tar; `ruri/r` вызывает интегрированный Ruri. [`README.md`](https://github.com/RuriOSS/rurima/blob/30a0637331a95b05377e3ea2e36d52b13d1a94f7/README.md) *прямо* заявляет отсутствие OCI compliance и только `PARTIAL` замену Docker. Не считать `rurima r` drop-in для `docker run` или `podman run`, стандартные OCI image-spec/runtime-spec, compose, networks, secrets, volume, registry sign/attestations, CNI/Netavark, lifecycle/metrics не подтверждены.
- **VERIFIED — бинарник статический, команды внешние:** `src/checkdep.c:33–80` проверяет `tar`, `curl`, `file`, `gzip`, `xz`; `src/dockerhub.c` вызывает `jq` и `sha256sum` (часть путей); `src/archive.c` вызывает `proot` для rootless unpack. `Makefile`, `CMakeLists.txt` используют GNU C, `libcap`, `libseccomp` и submodules. Отличать переносимый *rurima binary* от всей runtime dependency closure.
- **VERIFIED — режимы изоляции различаются:** pinned [`Ruri README`](https://github.com/RuriOSS/ruri/blob/711673a7b2a1e3c5d2a77a6085f2e082e8fd5d56/README.md) и [`Ruri USAGE`](https://github.com/RuriOSS/ruri/blob/711673a7b2a1e3c5d2a77a6085f2e082e8fd5d56/doc/USAGE.md): `chroot` по умолчанию при ограниченных kernel features, `unshare` с namespaces и `pivot_root` при наличии соответствующих возможностей ядра, `--rootless` через userns+`uidmap`. PRoot имитирует root/path translations для ограниченного устройства, но не предоставляет kernel namespace/cgroup isolation. Нельзя из «works without namespaces/cgroups» вывести «secure isolated container» — это альтернативный низкоизоляционный режим.
- **VERIFIED — network isolation неполная:** [`doc/FAQ.md:19–20`](https://github.com/RuriOSS/rurima/blob/30a0637331a95b05377e3ea2e36d52b13d1a94f7/doc/FAQ.md#L19-L20) прямо говорит, что Rurima не предоставляет сетевую изоляцию; pinned Ruri USAGE указывает `-x` option (disable network), `NET` and `USER` namespaces are not fully supported. WIP `rurima netns` и `net_wrapper.sh` — не доказанный hard boundary для чужих программ. [`doc/Security.md` Ruri](https://github.com/RuriOSS/ruri/blob/711673a7b2a1e3c5d2a77a6085f2e082e8fd5d56/doc/Security.md) советует rootless/unshare/NO_NEW_PRIVS/seccomp, но эти механизмы не становятся автоматически активными при работе в fallback chroot.
- **VERIFIED — privilege management:** [`src/main.c`](https://github.com/RuriOSS/rurima/blob/30a0637331a95b05377e3ea2e36d52b13d1a94f7/src/main.c) проверяет SUID/SGID/capabilities процесса в `detect_suid_or_capability()` и отклоняет их; README предлагает sudo там, где нужны привилегии, и предупреждает о `--privileged`. Запуск root + chroot, особенно с mounted host resources, — не безопасное исполнение недоверенного workload.
- **VERIFIED — OCI registry digest проверяется условно:** [`src/dockerhub.c:632–650`](https://github.com/RuriOSS/rurima/blob/30a0637331a95b05377e3ea2e36d52b13d1a94f7/src/dockerhub.c#L632-L650) checksum gate `if (!fallback && rurima_sha256sum_exists())`: при `--fallback` **или при отсутствии `sha256sum`** нет видимой byte-for-byte валидации скачанного Docker layer по digest в этой ветке. [README](https://github.com/RuriOSS/rurima/blob/30a0637331a95b05377e3ea2e36d52b13d1a94f7/README.md) говорит о forced fallback for `ghcr.io`. Не утверждаем взлом/несовпадение неизбежны, но режим несовместим с требованием mandatory checksum before extract для воспроизводимого build/supply chain.
- **VERIFIED — OTA доверяет latest release transport:** [`src/subcommand.c:698–793`](https://github.com/RuriOSS/rurima/blob/30a0637331a95b05377e3ea2e36d52b13d1a94f7/src/subcommand.c#L698-L793) получает `commit-id.txt`, скачивает `latest/download/{arch}.tar`, распаковывает во временный каталог и вызывает `cp -f rurima /proc/self/exe` target; явная проверка хэша/подписи скачанного архива в этой функции **не обнаружена**. Установочный пример `. <(curl -sL https://get.ruri.zip/rurima)` исполняет удалённый shell. Ни одно из них не запускать в production/локальном рабочем профиле, pin self-updater disabled и запрет egress для испытаний.
- **VERIFIED — archive extraction boundary требует проверки:** [`src/archive.c:48–165`](https://github.com/RuriOSS/rurima/blob/30a0637331a95b05377e3ea2e36d52b13d1a94f7/src/archive.c#L48-L165) построение tar command `-xpf/-xpzf/-xpJf` с `-C dir`, иногда через `proot`; прочитанный код не доказывает запрет malicious symlink/path traversal/archive layer whiteouts/device nodes/external writes в любых комбинациях. **Не заявляем exploit без test**, но и не считаем независимым extract sandbox, особенно при root и LXC mirror.
- **VERIFIED — CI/control scope:** `.github/workflows/build.yml` содержит release/build paths по архитектурам, `codeql.yml` запускает анализ; pinned tree не содержит отдельного тестового каталога и репозиторий не демонстрирует OCI conformance/security/adversarial runtime suite. Наличие CI badges, MIT и статического бинарника не означает test coverage или OS isolation assurance; benchmarks CPU/IO/memory **не найдены/не воспроизводились**.

## 2. Tradeoffs по системе

| Режим / цель | Потенциальная выгода | Safety / portability limitation |
| --- | --- | --- |
| Minimal Linux/Termux: extract trusted rootfs | Меньше внешних контейнерных сервисов, можно получить Docker/LXC rootfs и собрать архив | tar/curl/jq/proot и PRoot limitations; rootless image unpack != secure rootless execution; нет OCI |
| Standalone chroot trusted distro | Простое ручное исследование/ремонт файловой системы, без Docker daemon | Нет kernel network/PID/mount/cgroup isolation при отсутствии namespaces, требуются root или PRoot; нельзя считать sandbox |
| Ruri unshare/rootless | Снижение привилегий при наличии namespaces/userns, некоторые seccomp/cgroup options | Needs kernel support/uidmap, а NET/USER namespace support неполный; независимо нужны security controls и тесты |
| Bazzite + existing rootless Podman | Rurima мог бы делать необычный one-shot image extraction | Дублирует `podman/skopeo` image handling, меньшая совместимость OCI/supply-chain; YAGNI unless reproducible win |
| Scientific sandbox (Paper2Project) | Возможная гипотеза экономии размера/runtime setup | Потеря OCI/rootless isolation, checksum gating, egress control, reproducibility — **неприемлемо без hard security evidence** |
| Download fallback / OTA | Совместимость registry и простота обновления | SHA-256 layer check skipped, OTA no visible artifact signature check; запрещать в контролируемом эксперименте |

## 3. Screening 45 проектов, приемка и A/B/C

[Project registry `Artemedi/project-registry@91a0ca742a3225f6c4683b51031e8bbb595fdab8`](https://github.com/Artemedi/project-registry/tree/91a0ca742a3225f6c4683b51031e8bbb595fdab8): все 45 `PROJECT.md` просмотрены документально; **2 architecture/comparator candidates**, прочие 43 `DEFERRED_SCREENING`. Цель не заменить Podman, а проверить отдельно допустимость `pull/unpack` для trusted/synthetic rootfs (не запуск образа).

1. **`dsh-paper2agent`**: registry сообщает изолированные эксперименты rootless Podman; решение Rurima **отклонить как runner replacement**, пока нет parity с OCI isolation, network deny, resource quotas и image provenance. Низкорисковая гипотеза: можно ли *выделить только этап ручного чтения файловой структуры архивов* на синтетическом rootfs, не передавая данные во внешний registry и не выполняя бинарник Rurima. Это статическая reference comparison, no deployment authorization.
2. **`Harness`**: deployment/probes и интеграционная рабочая область; теоретически rootfs format handling можно сопоставить с Podman/skopeo в disposable ephemeral CI/test lab, без использования Rurima для запуска service/agent и без изменения native deployment. Никакой подтверждённой потребности, интерфейса или performance benefit ещё нет.

**H1:** на доверенных детерминированных мини-образах Rurima способен снизить overhead *извлечения rootfs* без потери целостности, безопасности и фиксированного provenance. **H0:** отсутствие OCI/verification, внешние dependencies и отсутствие преимуществ на Bazzite делают его хуже incumbent Podman/skopeo.

- **A**: установленный rootless Podman/containers-image/skopeo, точные версии, rootless UID, synthetic OCI archive, no network, offline source, run nothing.
- **B**: статическая offline проверка pinned Rurima extraction semantics по коду; без запуска. Pin image digest и reject при `fallback`, отсутствующем `sha256sum`, неподтверждённом tar signature, unsafe symlink/device entries.
- **C**: только после отдельного security signoff — standalone disposable VM с immutable snapshot, unprivileged user, outbound firewall deny, zero credentials, no shared mounts, trusted synthetic layer archive; runs extraction **only**, не `ruri container`, не OTA, не `--privileged`. Функциональные тесты проверяют exact file tree/hash, modes, hard/sym links, whiteouts and malformed archive guard. Пилот Rurima требует независимого review и владельца.
- **Metrics**: extracted file hash/provenance and metadata parity, extract wall/CPU/RSS/IO, binary + dependencies footprint, command invocations, network destinations, complexity, reproducibility, rootless userns/cgroup/seccomp state, denied read/write escape attempts and failures on malicious archives.
- **Hard gates:** 0 outside-rootfs writes, 0 unapproved network, all layers pinned and SHA-verified, no privilege escalation, lossless exact synthetic extraction, measurable advantage over Podman. Otherwise `REFERENCE_ONLY/NO_BENEFIT`.

**Decision:** `DOCUMENTED_CANDIDATE / NEEDS_EVIDENCE / BENEFIT_UNPROVEN / NOT_PRODUCTION_APPROVED`. Rurima isn't suitable for executing unknown agents or source-code experiments with confidential data; do not replace working rootless Podman.
