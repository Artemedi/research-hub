# MCP Toolbox и Wiki_PG — настройки PostgreSQL

Дата записи: 2026-11-04. Перенос структуры: 2026-11-05; выводы и область проверки сохранены.

**Дата:** 2026-11-04. **Статус:** `BOTH_MCP_EXECUTED / CONTRACTS_VERIFIED / DIFFERENT_SEMANTICS / NO_PRODUCTION_APPROVAL`.

## Вопрос

Может ли [MCP Toolbox for Databases](https://github.com/googleapis/mcp-toolbox) заменить или дополнить `Wiki_PG` для DBA-диагностики? Проверен **один пересекающийся сценарий**: прочитать PostgreSQL GUC с правильным значением, единицами и временем наблюдения. Вывод нельзя распространять на search, backup status, cluster inventory и весь функционал.

## Реальные версии, источники, тестовый контур

- **MCP Toolbox:** скачанный исполняемый [официальный v1.15.0 linux/amd64](https://storage.googleapis.com/mcp-toolbox-for-databases/v1.15.0/linux/amd64/toolbox), `toolbox --version = 1.15.0+binary.linux.amd64.8e8e569`. SHA-256 **загруженного** файла: `f6fac005c39898a379523700727a2a3d0a2828f579bec22cc0efe74e0652062d` (запись фактического артефакта, не проверка подписи upstream). [Срез исходников main@3e536bb](https://github.com/googleapis/genai-toolbox/tree/3e536bb683c914b26bdf9046a65b805a160af8dc) изучался отдельно: *этот SHA не объявляется SHA бинарника релиза*.
- **Wiki_PG:** [Artemedi/Wiki_PG@d55721b](https://github.com/Artemedi/Wiki_PG/tree/d55721bb99bff25fae352341cfd630c048693d6b), `Wiki_PG/ingestion/mcp_wiki_server.py`, инструмент `get_postgres_setting`, настоящий `FastMCP`. Репозиторий не изменялся.
- **Среда:** Bazzite, Podman `postgres:18.3` в disposable контейнере `trin-toolbox-lab-20261104` с `--network none`, `--memory 768m`, `--cpus 1`, `--pids-limit 120`. MCP Toolbox работал через stdio **внутри** контейнера, подключался к PostgreSQL через `127.0.0.1:5432`; Wiki_PG через stdio Python MCP SDK на Bazzite и читал **только** подготовленные файлы. Лабораторная PostgreSQL без внешнего порта.
- **Доступ:** тестовая роль `observer LOGIN`, `CONNECT`, `default_transaction_read_only=on`, **нет** grants на пользовательскую таблицу `fixture`. Попытка `INSERT` даже после отдельного `SET default_transaction_read_only=off` завершилась `permission denied for table fixture`; количество строк осталось **1**. Сеансовые GUC — не граница безопасности; решающими являются привилегии БД и узкий фиксированный SQL.
- **Один разрешённый инструмент Toolbox:** `postgres-sql` с текстом `SELECT name, setting, unit FROM pg_catalog.pg_settings WHERE name = $1`, **bind-параметр** `setting`. Никакого произвольного `execute_sql` или `--prebuilt postgres` в эксперименте не было. Файл конфигурации: [только для disposable lab](../../experiments/2026-11-04-mcp-toolbox-wikipg-tools.yaml).
- **Два снапшота Wiki:** `LAB_001` с `captured_at=2026-11-04T07:00:00`, который **намеренно сформирован из текущего** `pg_settings`; второй `2026-11-03T07:00:00` с искусственным `work_mem=8192`. В исходных данных не используются реальные серверы пользователя или production логи. У совпадения новых значений общее происхождение; оно проверяет транспорт MCP и контракты, **не независимость двух источников**.

## Проверки MCP, независимый oracle

Инициализировались **реальные MCP stdio** сеансы: `ClientSession.initialize()`, `list_tools()`, `call_tool()`. Toolbox зарегистрировал **1** инструмент; Wiki_PG зарегистрировал **12**, но проверялся только `get_postgres_setting`. Независимый контроль — `psql` запрос к `pg_catalog.pg_settings` внутри disposable lab.

| GUC | Oracle (setting, unit) | Toolbox live | Wiki latest snapshot | Вывод |
| --- | --- | --- | --- | --- |
| `max_connections` | `100`, unit отсутствует | `100` | `100` | PASS |
| `random_page_cost` | `4`, unit отсутствует | `4` | `4` | PASS |
| `wal_level` | `replica`, unit отсутствует | `replica` | `replica` | PASS |
| `work_mem` | `4096 kB` | `4096 kB` | `4096 kB`, точные 4 MiB | PASS |

Всего **80/80** измеряемых ответов *каждого* MCP инструмента корректны: 4 GUC × 20 вызовов после двух прогревочных на каждый GUC. Сравнение `unit=None` и `unit=""` нормализовано как отсутствие единицы измерения. Предусмотрен `source_file` и `captured_at` в Wiki_PG; у live SQL Toolbox таких исторических полей нет.

**Запрос истории:** `Wiki_PG get_postgres_setting(host=LAB_001,parameter=work_mem,snapshot_date=2026-11-03)` возвращает **8192 kB** с корректным source_file; для 2026-11-01 возвращает **`status=no_snapshot`**, не подменяет дату. *Важно:* в последнем сценарии **`isError=false`**: MCP клиент обязан проверять поле `status`, а не трактовать любой не-error response как наличие факта.

**Искусственное устаревание:** после `ALTER SYSTEM SET work_mem TO '8MB'` + `pg_reload_conf()` в **одноразовой БД** Toolbox вернул **8192 kB**, а последний неизменённый снимок Wiki_PG — **4096 kB**, как и должен. `ALTER SYSTEM RESET work_mem` + reload выполнены в `finally`; независимый psql подтвердил возвращение к **4096 kB**. Это **не дефект Wiki_PG**, а его явно задокументированный temporal contract.

**Некорректный пользовательский ввод:** строка с `DROP TABLE` в поле `setting` обработана Toolbox как **bind parameter**, результат — пустые строки, без исполнения DDL. Wiki_PG отклонил имя параметра со статусом `invalid_parameter`. Контрольная таблица после тестов имела прежнее число строк. Тест не является аудитом всех типов инструментов или защитой от всех SQL-инъекций.

## Overhead: micro-lab, не производственный benchmark

Условия: 20 прогретых RPC на каждый GUC и инструмент, без других пользовательских запросов; один клиентский процесс инициирует два отдельных MCP stdio сервера **последовательно**. Toolbox — Go-процесс через `podman exec`, Wiki_PG — host Python. Поэтому нельзя нормировать показатели до истинной нагрузки PostgreSQL, общего CPU cost или production p95.

| Измерение, второй полный прогон | Toolbox | Wiki_PG |
| --- | ---: | ---: |
| Инициализация до MCP handshake, включая транспорт | **135.0 мс** | **339.1 мс** |
| `work_mem`, median `call_tool` | **0.759 мс** | **1.269 мс** |
| `max_connections`, median | **0.745 мс** | **1.306 мс** |
| `random_page_cost`, median | **0.747 мс** | **1.265 мс** |
| `wal_level`, median | **0.774 мс** | **1.259 мс** |
| Размер сериализованного SDK `CallToolResult.model_dump_json` для `work_mem` | **183 B** | **7157 B** |

Размер означает **client-side сериализацию результата SDK**, а не сетевые байты на транспортном уровне и не чистый размер SQL row. Wiki_PG включает заметно более богатую provenance/interpretation и может сериализовать одинаковые сведения в `content` и `structuredContent`. Во втором прогоне эти медианы устойчивы по порядку величины; у первого прогона `work_mem` были **0.783/1.319 мс**. **Вывод про сравнительный CPU/p95 в реальной инфраструктуре делать нельзя.** Нет проверки десяти тысяч GUC, количества соединений под параллельностью, LAN/TLS и ограничений на RAM/IO.

## Безопасность и интеграционные нюансы

1. На `postgres-sql` Toolbox v1.15.0 при default tool annotations возвращены **`readOnlyHint=false`, `destructiveHint=true`**, несмотря на фактический фиксированный SELECT. Это **метаданные аннотаций**, не разрешение SQL. Конкретный инструмент безопасен от записи в лабе потому, что SQL фиксирован, параметры bind и роль не имеет write-grants. Source Go main checkout имеет `IsReadOnly() = false`; runtime-энфорсинг по аннотации не подразумевается.
2. Toolbox в startup logs выводил предупреждение об `allowed-origins=*` и `allowed-hosts=*`. В этом опыте использован **stdio, без опубликованного HTTP listener**. Если выбран HTTP transport в иной среде, restrict origins/hosts и auth отдельно; этот тест не валидирует защиту HTTP.
3. Wiki_PG содержит иные инструменты для документов, исторических снимков, реестра кластеров, backup-status и интерпретации. Toolbox — универсальный SQL/MCP framework. **Replace Wiki_PG with Toolbox — неверная постановка задачи.** Возможная интеграция: отдельный *опциональный* read-only live fact tool с учётом `host`, `database`, `capture_time`, `source_kind`, отказа при недоступности live connection и запрета динамических SQL statements.
4. Не добавлять default prebuilt-toolset без отдельного аудита разрешений и типов инструментов. Не выводить доступные в snapshot Wiki_PG значения как «настройка сейчас».

## Репродукция на отдельной машине

Скрипты: [сборка fixture](../../experiments/2026-11-04-mcp-toolbox-wikipg-fixture.py), [настоящие MCP вызовы и oracle](../../experiments/2026-11-04-mcp-toolbox-wikipg-compare.py), [конфиг Toolbox](../../experiments/2026-11-04-mcp-toolbox-wikipg-tools.yaml). Ниже `$LAB` — временный каталог, в котором лежат `Wiki_PG/` clone, `bin/toolbox`, `venv`, `toolbox-config.yaml`; repo `research-hub` клонировать отдельно или заранее.

```bash
LAB=/tmp/mcp-toolbox-wikipg-20261104
mkdir -p "$LAB/bin"
git clone https://github.com/Artemedi/Wiki_PG.git "$LAB/Wiki_PG"
# Для точной репликации: git -C "$LAB/Wiki_PG" checkout d55721bb99bff25fae352341cfd630c048693d6b
curl -fL https://storage.googleapis.com/mcp-toolbox-for-databases/v1.15.0/linux/amd64/toolbox -o "$LAB/bin/toolbox"
sha256sum "$LAB/bin/toolbox"
chmod +x "$LAB/bin/toolbox"
uv venv "$LAB/venv"
uv pip install --python "$LAB/venv/bin/python" 'mcp>=1.9,<2' requests PyYAML psutil pytest
cp experiments/2026-11-04-mcp-toolbox-wikipg-tools.yaml "$LAB/toolbox-config.yaml"

podman run -d --name trin-toolbox-lab-20261104 --network none \
  --memory 768m --cpus 1 --pids-limit 120 --pull=missing \
  -e POSTGRES_HOST_AUTH_METHOD=trust \
  -v "$LAB/bin/toolbox:/usr/local/bin/toolbox:ro,Z" \
  -v "$LAB/toolbox-config.yaml:/tmp/tools.yaml:ro,Z" postgres:18.3
# Дождаться podman exec trin-toolbox-lab-20261104 pg_isready -U postgres.
podman exec trin-toolbox-lab-20261104 psql -U postgres -c "CREATE DATABASE lab"
podman exec trin-toolbox-lab-20261104 psql -U postgres -d lab \
  -c "CREATE ROLE observer LOGIN; GRANT CONNECT ON DATABASE lab TO observer; ALTER ROLE observer SET default_transaction_read_only=on; CREATE TABLE public.fixture (id integer primary key, value text); INSERT INTO public.fixture VALUES (1, md5('1'));"

"$LAB/venv/bin/python" experiments/2026-11-04-mcp-toolbox-wikipg-fixture.py --root "$LAB"
"$LAB/venv/bin/python" experiments/2026-11-04-mcp-toolbox-wikipg-compare.py \
  --root "$LAB" --repetitions 20 --staleness-check
podman rm -f trin-toolbox-lab-20261104
```

`POSTGRES_HOST_AUTH_METHOD=trust` здесь допустим **только в disposable контейнере с отключённой сетью** и не является примером production-auth. Source `tools.yaml` содержит фиктивный пароль, не реальные реквизиты. Скрипт `--staleness-check` **отказывается** запускать `ALTER SYSTEM` в контейнере с другим именем, а затем восстанавливает настройку в `finally`. Тем не менее **никогда не применять этот тест к реальной БД**. Удалять тестовый контейнер нужно после проверки.

## Верификация, применимость, решение

- Запущено **17/17** unit/contract тестов Wiki_PG из `test_mcp_wiki_server_pg_setting.py`, `test_mcp_stdio_contract.py`, `test_mcp_pg_settings_fastpath.py`; 0 failures (отдельное virtualenv). Это проверка subset, не всего Wiki_PG/Chroma.
- MCP Toolbox протестирован исполняемым бинарником, его Go tests локально не исполнялись (Go toolchain отсутствует). Не заявлять полную совместимость конфигураций Toolbox.
- **Решение:** `COMPLEMENTARY_CAPABILITIES / LIMITED_LAB_PASS / INTEGRATION_BLOCKED`. Для Wiki_PG разрешена **гипотеза** об опциональном live read-only источнике; не заменять существующие historical/query/backup инструменты. Для решения о внедрении требуется однозначный temporal contract и тесты доступа, privilege boundaries, 30+ размеченных DBA-инцидентов, 15/18 PG, replica, concurrency, CPU/IO, p95 и обработка несоответствий live vs snapshots.

**Изменений кода Wiki_PG, системных MCP-конфигураций, production PostgreSQL или настроек агента не было.**
