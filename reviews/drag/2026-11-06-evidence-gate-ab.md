## Гипотеза, исходники и границы

Проверяется узкий механизм: может ли **проверка достаточности метаданных** отклонять запросы без полноценного evidence, а **переход по явно связанному документу** восстанавливать полный набор ссылок для multi-hop. Реальный повторно используемый исходник — класс `BM25` из [ранее закреплённого локального скрипта](../../experiments/2026-11-06-drag-retrieval-depth-ab.py), SHA-256 файла `acc0a7381cf70fc7773255f642c3fd549b2c63f5d7954d26d5521d459b8d3169`; остальные ветки — созданный для лаборатории Python-код, **не код DRAG** и не реализация целевого проекта.

**Данные и oracle:** 3 независимых calibration seeds (`20261120..20261122`), затем **новые** 5 holdout seeds (`20261211..20261215`). В каждой выборке 12 тем, 96 искусственных DBA-документов и 84 запроса (12 запросов каждого из 7 классов). Весь holdout — **420 запросов**: 180 с правильными доказательствами (single, alias, linked_pair) и 240 без полного правильного набора (absent event, несовместимая пара code/marker, отсутствующий runbook, ссылка на чужой runbook). У calibration и holdout разные наборы тем и порядок полей в текстах, но **одна известная машиночитаемая схема**.

Источник истины — отдельно сгенерированный структурный manifest `query → gold document IDs` с истинной связью observation/runbook, не вывод BM25 и не решение guard. Gold не читается поисковыми функциями. Это **не независимая человеческая разметка**: генератор и oracle построены одним автором, поэтому ожидать переноса показателей на real-world RAG нельзя. В JSON сохранены все `per_query.gold` и citations для повторного пересчёта.

**Calibrated gate:** допустимые уровни совпадения metadata `0.5 / 0.75 / 1.0`; заранее заданная функция выбора `fully_grounded + 0.15×coverage − 3×false_answer_negative` на calibration, без доступа к holdout. `0.75` и `1.0` дали одинаковую калибровочную utility `1.15`; правило выбора при равенстве предпочитает более строгий `1.0`. Его зафиксировали **до подготовки новых holdout seeds**, а затем не корректировали по результатам.

**5 сравниваемых вариантов**, одинаковый выходной лимит `top-K=3` и одинаковый базовый BM25 по уже созданному индексу:
1. Baseline: BM25 top-3 без проверки.
2. Schema-only: BM25 → candidate с `kind=observation`, `subsystem/event/marker/alias` при confidence ≥1.0, **без follow**.
3. Follow-only: BM25 → первый observation → связь с runbook, **без проверки соответствия запросу**.
4. **Gate+Follow:** BM25 → строгий observation guard → для `need both` проверить `next` и обратное `for_incident`; при неполном evidence возвращать пустой набор.
5. Wrong-link negative control: тот же guard и lookup budget, но намеренно выбирается **другой** runbook. Должен провалить полноту multi-hop.

**Существенное ограничение:** второй этап — O(1) lookup по явно записанному ID, **не полноценный второй ranked retrieval** и не reasoning model; измерение этой лаборатории нельзя представлять как производительность DRAG/RAG.

| Только правильные документы, без лишних | 0% | 66,7% | 33,3% | **100%** | 66,7% |
| Охват положительных запросов | 100% | 100% | 100% | **100%** | 100% |
| Корректный отказ среди 240 отрицательных | **0%** | 50% | 0% | **100%** | 50% |
| Точность всех выданных цитат | 14,3% | 60% | 20% | **100%** | 37,5% |
| Mean CPU на 84 запроса | 45,56 мс | 52,40 мс | 49,18 мс | **50,43 мс** | 50,05 мс |
| Mean wall на 84 запроса | 45,77 мс | 52,63 мс | 49,40 мс | **50,67 мс** | 50,29 мс |
| Mean p95 одного запроса | 0,625 мс | 0,744 мс | 0,713 мс | **0,710 мс** | 0,732 мс |
| In-memory link lookups / seed | 0 | 0 | 12 | **36** | 36 |

У всех веток выполняется **8064 BM25 document-score operations** на 84 запроса, поскольку сам BM25 одинаковый и не углубляется за пределы начальных top-3. Gate+Follow добавляет ~**10,7% CPU/wall** относительно BM25 в синтетическом Python-microbenchmark; overhead включает чтение метаданных и 36 дешёвых lookup в памяти, но **не сетевой поиск или модель**. Отсутствие false citations здесь обусловлено искусственно машиночитаемыми полями и известным графом.

**Ресурсные показатели:** `tracemalloc` средний Python peak около 29,3 KB (BM25) и 33,9 KB (Gate+Follow), что **не** равно resident RAM; общий process RSS highwater достиг около 26 MB и не атрибутируется одному arm. `/proc/self/io` за timed evaluation: physical `read_bytes/write_bytes=0/0` (индекс в памяти), `rchar≈102` включает диагностическое чтение `/proc`, а не чтение корпуса с диска. Создание корпуса и сохранение JSON вне timing. **VRAM:** `N/A`, **LLM tokens:** `N/A`, **API costs:** 0 USD, так как внешние API, платные модели и GPU не использовались. Модель экономии LLM-токенов здесь отсутствует.

**Итог внутреннего holdout:** условно положительный для **схемного guard + graph following**, но никаких выводов о качестве реального RAG. Wrong-link control восстановил лишь 75% recall и не завершил multi-hop, то есть сам факт дополнительного lookup не объясняет выигрыш без правильной структуры ссылок.

## Негативная проверка OOD (отдельная, post-hoc)

Дополнительно **пять новых seeds 20261231..20261235**, 84 запроса на seed, неизменный gate `1.0`. Это **не второй слепой holdout**: adversarial сценарии разработаны уже после просмотра результатов первого holdout, поэтому описываются как диагностическое нагрузочное/устойчивостное тестирование, без статистических выводов о production.

| Корпус | Gate+Follow: positive fully grounded | Coverage positives | Correct abstention negatives | Citation precision | CPU / 84 запроса |
| --- | ---: | ---: | ---: | ---: | ---: |
| Исходная машиночитаемая схема | 100% | 100% | 100% | 100% | 50,07 мс |
| **Format shift:** `kind=observation` → `kind:observation` | **0%** | **0%** | 100% | **N/A** — все цитаты отсутствуют | 49,72 мс |
| **Source poisoning:** четыре поддельные schema-compatible observation на инцидент | **0%** | 66,7% | 100% | **0%** — все выданные цитаты неверны | 93,54 мс |

Format shift сохраняет лексические токены BM25: отдельный тест подтвердил **идентичные BM25 top-3** до/после замены `=` на `:`. Следовательно потеря полноты обусловлена именно жёстким metadata parser, а не изменившимся retrieval. Для poisoned corpus число документов на seed увеличено с 96 до 144, fake records имеют документно-правдоподобные поля, но не принадлежат авторскому ground truth. Guard обнаруживает, что runbook не привязан к fake anchor, **для multi-hop**, однако пропускает fake observation **для одношаговых/alias** запросов. Это демонстрация того, что синтаксическая проверка не является проверкой доверенного происхождения.

Дополнительные физические IO и генерация fake docs вне timed retrieval; CPU/latency на 144 документа не сопоставимы напрямую с 96-документным корпусом без нормализации размера.

## Неудачный первый запуск и closed-loop проверки

**Изначальный запуск невалиден:** `field_map` читала идентификаторы ссылок regex-значением `[a-z0-9_]+`, обрезая дефисы; в итоге связанные runbook никогда не находились, что видно по нулевому multi-hop completion. Исходный invalid JSON [архивирован со статусом INVALIDATED](../../data/results/drag/2026-11-06-invalidated-parser-run.json), исходный SHA-256 `9e72dfe14fc826b294d3ca8e59365d52895b12da93dc605c47ee3ab6fc7686dc`, **не включён в оценку**. Исправлена только поддержка дефисов в metadata, добавлен обязательный positive control 12/12 для linked_pair, калибровка заново выполнена **только на dev**, а старые test seeds `20261201..20261205` исключены и заменены новыми `20261211..20261215`. Не утверждается криптографически слепой протокол: разработчик видит генератор данных.

Позднее диагностический OOD-агрегатор упал при попытке усреднить `None` — precision не определён, когда нет ни одной цитаты. Исправлен только агрегатор: сохраняет **N/A**, не подменяет нулём. Пересмотрены и исходники, и табличные результаты, подтверждение воспроизводимости и unit-verify см. JSON.

**Негативный oracle control:** изменение gold ID правильного случая меняет измеренную точность, не меняя результат retrieval. **Другой negative control:** заведомо неверно выбранный linked runbook проваливает multi-hop completion. В наборе regression tests отдельно проверены hyphenated IDs, отсутствующие/чужие ссылки, несовместимые code/marker, неизменность BM25 после format shift и срыв precision при документах-подделках. Синтетическая data leakage исключена на уровне функций поиска (им не передаётся gold), но не на уровне выбора автором структуры экспериментальной задачи.
