# Where LLM agents get stuck debugging databases — field-study review

**14.11.2026, новая работа от 12.11:** [arXiv 2611.17304v1](https://arxiv.org/pdf/2611.17304v1), 12 pp, sha256 54a9e5744bcb6e801e60b0a647c3dee77fb28db40a48a15ed0603d32a8923dda. Изучены полный текст, sampling/analysis, all incident outcomes, validity threats и авторские предложения. Не воспроизведена полевая история одной компании; исходные транскрипты закрыты.

## Methodology / observations

Ретроспектива восьми database incidents в message-dispatch системе за десятидневный период, 27 agent sessions и порядка 3000 tool calls. Основной coder взаимодействовал с Claude Code, но большинство запросов в платформе обслуживал open-weights provider (~79%); отдельные причины не привязаны к модели. Двадцать два fix commits в сумме за 8 incidents; пять concurrency-dependent cases имели начальные ложные диагнозы и исправления. Данные реконструированы по журналам и версиям кода, критерии false start требуют последующего опровержения в транскриптах/коммитах. Важные gaps: недоступные мгновенные pg_locks и pg_stat_activity, усечённые deadlock traces, неидентичный sandbox/production контекст и невозможность воспроизвести конкурентную нагрузку. На пяти concurrency-кейсах все имели access gaps, в четырех совместно с reasoning issues. Выводы относятся к этой группе, не доказывают, что доступ причинно доминирует во всех инцидентах.

## Limitations and actionable design

Нет рандомизации access/model, только одна фирма/одна команда, восстановление после факта, закрытые raw records, использование того же агента для помощи автору при подготовке работы; автор отдельно признаёт risk to validity. Нельзя оценивать причинный эффект новых привилегий. Источник призывает к узкому audited forensics API и flight recorder для transient traces, **а не** к передаче production credentials модели.

[sequential-rca@13fa0c9/src/sequential_rca/orchestrator.py:1–100](https://github.com/Artemedi/sequential-rca/blob/13fa0c910c75d9e3b79c758bcba473a6406e008c/src/sequential_rca/orchestrator.py#L1-L100) проверяет evidence IDs и допускает INSUFFICIENT_EVIDENCE; offline run уже умеет квалифицировать отсутствие источников. [Wiki_PG@d55721b/Wiki_PG/ingestion/diagnostic_snapshot.py:1–100](https://github.com/Artemedi/Wiki_PG/blob/d55721bb99bff25fae352341cfd630c048693d6b/Wiki_PG/ingestion/diagnostic_snapshot.py#L1-L100) различает incomplete/unavailable diagnostics, **не** предоставляет continuous locks capture. Не добавлять новые collectors/credentials без отдельного DBA approval.

Минимальный A/B: 12 synthetic историй блокировок и отсутствующих evidence; одинаковый hypothesis model; A только обрезанные снимки, B snapshot плюс заранее записанный deadlock/lock flight record с timestamp/scope. Независимый DBA oracle определяет поддержку причинного диагноза и допустимый abstention; измерять false causal claims, missing evidence flags, correct root attribution, p95, расходы. Коррелировать readback по capture clock, имитировать stale и отсутствующие результаты. Полностью без production, 4 CPU/4GiB, не утверждать статистически доказанную зависимость по малой выборке.
