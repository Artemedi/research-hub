## Methodology and author-reported results

Три benchmark: DS-1000 (1k Python questions), ODEX (~945 questions, частично отфильтрованных для library imports), BigCodeBench-Instruct (~1140). Шесть code-model output sources, включая Claude3/GPT4/GPT3.5 и open-source models. Сравнивали статические Pyright/Mypy, grammar-oriented detection, code repair и constrained decoding. Метрики разделены: execution rate ≠ pass@1 ≠ доля imaginary library features. Precision/recall измерялись на ошибках, в том числе отсутствующие attribute/import/module и type. Результаты авторов варьируют сильно: imaginary features возникают в 8.1–40% на исследованных настройках; статические анализаторы находят от 16 до 70% всех ошибок и 14–85% library feature hallucinations в конкретных условиях. После ручной проверки выявлена верхняя граница истинного обнаружения ~77%, поскольку динамические Python типы создают ложные positive. Repair может повышать проход тестов без снижения истинной доли library hallucinations; constrained generation снизила её лишь на некоторых данных ODEX, не универсально.

**Ключевое инженерное предупреждение:** tool-level статическая проверка полезна в конвейере только как детектор недостоверных API, но никогда не как доказательство того, что исправленный код работает, безопасен и воспроизводит научный метод. Нельзя переносить результаты Python на C# Roslyn analyzer без независимой валидации.
