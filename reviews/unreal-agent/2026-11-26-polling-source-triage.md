# Unreal Agent — проверка гипотезы об опросе статуса

26 ноября 2026 года

**Решение для DSH Runtime — оставить текущий планировщик.** В проверенном исходнике независимые инструменты уже запускаются параллельно. Отличие от Unreal Agent есть в моменте следующего запроса к модели. Трасс, по которым можно посчитать запросы только ради статуса, у нас пока нет. Перенос механизма и оценку экономии отложили до такого замера. [Первичный аудит](2026-11-06-source-audit.md)

## Что показали закреплённые исходники

| Проверка | Наблюдение |
| --- | --- |
| Обработка инструментов в Unreal Agent | Координатор принимает события операций. Завершившийся вызов становится новым входом для модели. Если соседние вызовы ещё работают, координатор ждёт короткий интервал, чтобы собрать их результаты. После этого следующий запрос может уйти с уже доступными результатами. |
| Проверка пакетирования в Unreal Agent | В опубликованном тесте три заранее поставленных в очередь завершения дают один запрос к подставной модели. Это проверка пакетирования. Она оставляет открытым вопрос о числе запросов, когда результаты приходят с большим интервалом. |
| Обработка инструментов в DSH Runtime | Планировщик исполняет независимую группу с ограничением параллелизма. Цикл модели ждёт завершения шага с группой. Эта граница может задержать работу по быстрому результату, но сама по себе не создаёт отдельный запрос модели для опроса статуса. |
| Измерение в DSH Runtime и agent-config | Существующие замеры продолжения сессии охватывают историю и работу с инструментами. Учёт DSH агрегирует токены попыток за ход и отдельно учитывает кэш. В просмотренных конфигурациях agent-config не найдено счётчика, который связывал бы причину запроса модели со статусом ожидающей операции. |

Исходник и тест Unreal Agent проверены по публичному коммиту. Для DSH Runtime и agent-config просмотрены закреплённые исходники проектов владельца. Один внешний тест прочитан. Замеры на запущенных координаторах и запросы к провайдерам не выполнялись. ## Условие для отдельного замера

В изолированном стенде с подставной моделью прогнать два независимых инструмента с одинаковым временем выполнения и с большим разбросом времени. У каждого вызова записать идентификатор, тип начала и завершения, а у запроса к модели — связь с доступными результатами. Запрос считать опросом статуса, если он вызвал только проверку состояния уже запущенной операции и не получил нового результата, сообщения пользователя или команды управления. Сверить итоговые результаты и число запросов. Отдельно проверить зависимую пару, где параллелизм меняет корректность, и доставку результатов после отмены. Показатели токенов и стоимости требуют отдельного прогона с моделью и снимком тарифа.

Если опросов статуса нет, гипотеза об их сокращении не даёт основания менять планировщик. Если быстрый результат регулярно ждёт медленного, это отдельная гипотеза о задержке. Для неё надо измерять время до первого полезного действия и число дополнительных запросов при сохранении результата. По HermesAgent и sequential-rca этот разбор новой оценки не даёт.
