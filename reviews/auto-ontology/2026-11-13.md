## Функциональный принцип

Source schema, column descriptions, SQL history и samples входят в семантическую compilation; LLM предлагает Terms, ColumnAttributes, SQL Attributes, Semantic Foreign Keys. PostgreSQL/pgvector хранит каталог и embeddings. Text-to-SQL агент ищет онтологию, строит SQL, выполняет parse и LLM intent validation и обращается к DB connector. MCP ограничен явно выбранными read oriented tools с авторизацией через frontend; это полезная грань, но не гарантия отсутствия ошибок бизнес-логики или отсутствия side effects.

## Подтверждённые source-level риски

1. **Cross-schema FKs:** [#463](https://github.com/NVIDIA/auto-ontology/issues/463); текущий [postgres.get_fks()](https://github.com/NVIDIA/auto-ontology/blob/fc43a82600e18b19d159c52023f54f5572f537ac/auto_ontology/connectors/postgres.py) имеет ошибочный join по tc.table_schema=ccu.table_schema; репортёр получил 39 из 98 FK в WideWorldImporters. Кодовое условие проверено, отдельный тест на базе не выполнялся.
2. **COUNT(*) rejection:** [#486](https://github.com/NVIDIA/auto-ontology/issues/486); в [sqlglot_extractor.py](https://github.com/NVIDIA/auto-ontology/blob/fc43a82600e18b19d159c52023f54f5572f537ac/auto_ontology/catalog/parsers/sqlglot_extractor.py) в выборку берутся только таблицы, у которых были атрибутированы колонки. COUNT(*) может не пройти validation при существующей таблице. End-to-end не воспроизведено.
3. **Unicode identifiers/PII:** [#468](https://github.com/NVIDIA/auto-ontology/issues/468), [#469](https://github.com/NVIDIA/auto-ontology/issues/469), ASCII-oriented regular expressions при преобразовании имен и PII detection; нужно проверить Cyrillic and mixed scripts на полном lifecycle.
4. **Out-of-scope stand-in:** [#497](https://github.com/NVIDIA/auto-ontology/issues/497) — при отсутствии ответа в подключённых источниках модель может выбрать семантически похожую, но неподходящую таблицу. Нужен fail-closed исход NOT_IN_CONNECTED_DATA, а не уверенный неправильный SQL.
5. **Credentials/PHI:** [connections.md](https://github.com/NVIDIA/auto-ontology/blob/fc43a82600e18b19d159c52023f54f5572f537ac/docs/connections.md) прямо говорит о plaintext JSON хранения UI credentials без Vault. Семантическая компиляция включает sample values в LLM prompts, Postgres коннектор читает SQL из pg_stat_activity. Нельзя использовать пациентские данные, production logs, секреты и несанкционированные provider endpoints.
6. **Нет MSSQL connector** в перечисленных движках. Для AKUZ и optimizer-twin прямое подключение не предполагается; можно проверить только искусственные/экспортированные структуры в PostgreSQL/SQLite. Авторизация инструментов не заменяет database-level read-only роль, sandbox и statement/IO budgets.
7. **Экономика:** sample/probe queries, FK overlap, embeddings, LLM и pgvector делают CPU/IO/RAM/latency сложнее простого schema-only поиска; на больших AKUZ схемах эти затраты не измерялись.

## Проектные гипотезы и обратимая стратегия

[Документальная матрица](../../portfolio/2026-11-13/source-project-fit.md) фиксирует akuz-schema-inventory, Wiki_PG и akuz-optimizer-twin только как PROFILE_MATCH / NEEDS_EVIDENCE. Настоящий source seam в целях не подтверждён, UI/inference/SQL не подключались.

Первый gate A: отдельный test-only Docker Compose, фиктивный PostgreSQL dataset и отдельный каталог, DB роль SELECT-only, сетевой deny/allow-list. Negative fixtures на межсхемный FK, кириллицу, COUNT(*), отсутствующий источник, невозможность исполнения DDL/DML. Любой провал является блокером для следующих стадий.

Gate B: 20–50 искусственных таблиц с gold relations, проверка semantic FK precision/recall, hallucinated JOINs, качество бизнес-терминов и storage/compilation costs. Gate C: 80–100 скрытых DBA-вопросов, замороженные модели и gold SQL; schema-only baseline vs ontology-assisted SQL, выполнение и сравнение результатов, false-but-plausible answers, abstention, latency, токены, pgvector/storage and I/O.

**Go** только при независимом улучшении execution accuracy, отсутствия новых критических false positives и приемлемой стоимости. Нет доказанного ROI, разрешения на production, изменения Runtime, доступа к реальным базам или принятия LLM как security boundary.
