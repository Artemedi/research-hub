# Claude Swarm + ZCode: 20 разных исследовательских задач, A/B/C и восстановление

**Дата эксперимента:** 2026-11-07. **Тип:** ограниченный лабораторный benchmark оркестрации, не научная экспертиза работ и не разрешение на внедрение. Предыдущие подтверждения: [репозиторный skill и первый live bridge](claude-zcode-swarm-skill-pilot.md), [обнаруженные дефекты upstream](claude-swarm-failure-injection.md), [минимальный patch](claude-swarm-repair-ab.md). ## Цель, первоисточники и oracle

Сравниваются три способа обработки **20 разных безвредных задач**, каждая состоит из одного отдельного абзаца доступной полной научной статьи и двух утверждений к нему (одно поддержано, второе опровергается/не поддерживается). **40 claim↔source случаев**, 20 различных SHA-256 абзацев, **10 пакетов по две задачи**. Метки записаны автором эксперимента заранее, скрыты от модели; после выполнения проверяются вне роя. Это **независимый от выходов ZCode authored oracle**, а **не** независимая слепая экспертная разметка.

## Три режима и равенство входов

- **A — single ZCode:** один прямой no-tool вызов на пакет (10 физических модельных обращений).
- **B — фиксированный совет:** два последовательных прямых no-tool вызова **того же промпта**; только единогласный SUPPORTED или NOT_SUPPORTED считается категоричным. Это избыточная двухвызовная проверка, **не** два независимых экспертных метода или разные модельные семьи.
- **C — adaptive DAG:** исходный `cj-vana/claude-swarm@31f19199bf3557cda4860231186a06b72c8edb94` с документированным [минимальным recovery patch](../../experiments/research-portfolio/2026-11-07-claude-swarm-recovery.patch.gz). Реальный `WorkerManager` запускает временный Git-worktree и частный tmux, подставляет разрешённый [CLI shim](../../experiments/research-portfolio/2026-11-07-zcode-claude-cli-shim.mjs), который вызывает локальный ZCode без инструментов, валидирует ответ и пишет session-qualified `.done`. Два узла в DAG: `primary`, условный `critic`, второй вызывается только если **заранее заданный** признак риска (числа, security/privacy source) или UNCERTAIN. Эскалация в **7 из 10** пакетов; 17 успешных worker-модельных вызовов в итоговом наборе.

**Контракт сравнения:** SHA-256 *первого* модельного промпта A/B/C идентичен для каждого из десяти пакетов. Входные источники, claim labels, роль модели, отсутствие доступных инструментов и предельная физическая параллельность **1** совпадают. Число обращений B и C **намеренно не совпадает**: сравнивается экономический компромисс повторной проверки, поэтому тест **не** является равнобюджетным сравнением интеллектуальных алгоритмов.

Измерения проводились последовательными режимами A→B→C на одном провайдере, поэтому серверный кэш и изменяющаяся нагрузка **мешают причинным выводам**. p95 — маленькие выборки физических model calls/batches; 20 task labels в одном paper связаны и не независимы статистически.

Превосходство Claude Swarm над direct ZCode **не доказано**. Избыточный совет может оказаться полезен на сложных ошибочных tasks, но таких случаев на этом маленьком корпусе нет.

## Найденный сбой: race в учёте tmux-сессии

**Первый запуск C:** 18/20 задач подтверждены, две из batch 8 остаются `BLOCKED_PROVIDER`, потому что `WorkerManager.checkWorker()` выдал `not_found` при проверке завершения сессии. При этом лабораторный лог shim содержал `BRIDGE_ACCEPTED_STRUCTURE`: ответ модели был структурно принят адаптером. Следовательно, эта ошибка **не является доказанной ошибкой модели или потерей содержимого**, а относится к наблюдению состояния worker. Указанный batch не был ошибочно принят на основании единственного `.done`.

**Вероятный механизм:** исходный `checkWorker()` вызывает `tmux list-sessions`, затем `tmux capture-pane`; если короткая сессия исчезает между вызовами, outer catch возвращает `not_found` даже при фактически созданных `.done`/`.exit`. Конкретное событие capture race в исходной сессии не записано, поэтому это **обоснованная гипотеза, не доказанная постфактум причина**.

**Адресный REWORK:** в исследовательском *координаторе*, а не в целевых исходниках, при `not_found` включены **не более трёх** повторных опросов с интервалом 150 мс; успешное состояние всё равно требует session-specific done+exit, структурно полного result JSON и совпадения хеша модельного промпта. Исходный checkpoint `c-08-primary` с ошибкой сохранён отдельно; повторён **только** этот заблокированный первичный вызов и его требуемый риском critic. Остальные пакеты использованы из checkpoints, **без повторных запросов**. После этого C = 20/20 и 17 успешных role receipts.

Независимый [synthetic tmux race](../../experiments/research-portfolio/2026-11-07-claude-zcode-tmux-race.mjs) использует настоящий `WorkerManager` и подставную команду `tmux`, которая **ровно один раз** возвращает ошибку `capture-pane`. Получается `not_found` при первом опросе, а ограниченный повторный опрос даёт `completed` по корректным маркерам: **5/5 оракулов**. Это воспроизводит **ветвь ошибки**, а не реальный CPU scheduling race на production.

## Crash/retry/duplicate и checkpoints

Дополнительная [fault-injection на синтетическом CLI](../../experiments/research-portfolio/2026-11-07-claude-zcode-failure-recovery.mjs) провела **17/17 проверок**: exit 7 после done остаётся crash, dirty Git worktree сохраняется, повторный старт того же feature ID fail-closed, захват конфликтного файла запрещён до явного `releaseAll`, копия прогресса проверяется SHA перед recovery, новая уникальная задача после ручного восстановления проходит независимый JSON oracle, duplicate accepted ID не исполняется. Одновременно подтверждён известный остаточный дефект: тот же Unix UID может подменить `.exit` на 0 и получить ложный `completed`; **внешний oracle** отказал без валидированного результата. Это **не защита от враждебного локального worker**.

**Идемпотентный replay:** повторные A, B, C верифицированы с **10/20/17 hits** и **0 новых provider calls** соответственно. Порча SHA входа у `a-00-solo` остановила процесс с `CHECKPOINT_INPUT_MISMATCH`, не приняв неправильный checkpoint. Проверка содержания checkpoint **не** криптографическая attestation от злоумышленника, который может перезаписать файл и ожидаемый hash; используются локальные доверенные каталоги. После провайдерского или оркестраторного отказа статус остаётся `BLOCKED`, пока причина не локализована; никакой бесконечной retry-политики.

## Накладные расходы и итог

Все модельные вызовы последовательны, **физическая concurrency 1**. Измерены per-call задержки и reported ZCode `input/output/cache tokens` в JSON. Замер CPU/RSS относится только к управляющему Node-процессу (A maxRSS ≈54 MiB, B ≈61 MiB, C ≈70 MiB); **не включает** ZCode subprocess, tmux и Git. Точных суммарных CPU/RAM/IO и внешней стоимости нет: `MEASUREMENT_MISSING` для production-расчёта. Отсутствуют реальные клинические данные, приватные сведения, автономные Bash/Write/Edit/MCP инструменты, публикация научных выводов, изменения чужих исходников и production.

По умолчанию продолжать использовать **прямой ZCode** для простых проверок; patched Claude Swarm применять только к измеримым coordination/recovery задачам в изолированной среде. Ни статус источников, ни карточки project-fit не повышать.
