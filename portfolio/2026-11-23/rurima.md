**Дата:** 2026-11-23. **Source pin:** [`RuriOSS/rurima@30a0637331a95b05377e3ea2e36d52b13d1a94f7`](https://github.com/RuriOSS/rurima/tree/30a0637331a95b05377e3ea2e36d52b13d1a94f7) (2026-09-07), MIT, static C program with pinned submodule Ruri. **Evidence-based interpretation:** `rurima pull/unpack/backup` works with image-rootfs content without Docker/LXC installed; integrated `ruri` runs it. The README admits it is **not OCI compliant** and only a partial Docker replacement. Its *binary* can be static, but Docker/image paths require external `tar`, `curl`, `file`, `gzip`, `xz`, JSON via `jq`, optional `sha256sum`, non-root extraction via `proot`; Ruri rootless needs userns and `uidmap`. Ruri chroot/PRoot without namespaces are weaker alternatives, not equivalent security sandboxes. Rurima FAQ disclaims built-in network isolation (pinned Ruri separately has limited unshare/`-x` behavior). No authored performance experiment or OCI conformance evidence in checked revision.

**Security/supply chain:** `src/dockerhub.c` verifies layer SHA-256 only if `!fallback && sha256sum_exists()`; fallback may be forced for GHCR. `src/subcommand.c` `rurima ota` pulls latest GitHub tar and copies binary over itself with no visible artifact signature/hash verification in that function. Archive extraction uses external `tar` under user privileges or `proot`; not shown to be a hardened untrusted archive sandbox. Never fetch/execute unknown image, `curl | shell`, OTA or rootful path in trusted workstation. Status `SECURITY_REVIEW_REQUIRED / NOT_PRODUCTION_APPROVED`.
