# JetStream — предварительный тест контракта для AKUZ Optimizer Twin

Порядок работ зафиксирован до прогона.

1. Проверить границу применения. Локальный Twin на `72a8b1e10ca3b199107fb2ff65ef24688a61cf29` сравнивает `EXPLAIN (FORMAT JSON)`. Для проверки возвращаемых строк нужен заполненный стенд. Используем одну искусственную таблицу `events(id, bucket, amount)` с 2 000 строками и NULL. Схема, строки и статистика AKUZ в стенд не входят.
2. Зафиксировать восемь запросов. Число строк, число ненулевых значений, SUM, MIN из групповых сумм, количество групп, количество строк по диапазону групп, результат по отсутствующей группе и исходные строки с NULL. Первые семь используют одно агрегированное состояние. Восьмой всегда возвращается к SQL. Штатный SQL PostgreSQL и DuckDB вычисляют ожидаемые строки из базовой таблицы. Порядок строк задаётся только там, где он нужен для сравнения.
3. Поставить отдельную тестовую реализацию из агрегатной таблицы и транзакционных триггеров. Сравнить все запросы после начальной загрузки, коммита вставки/обновления/удаления, отката, сброса состояния и перестройки. В двух подключениях удержать PostgreSQL-снимок `REPEATABLE READ` через коммит записи. Старый снимок должен видеть прежнее состояние, новый — новое. Контроль с намеренно устаревшим результатом должен расходиться с новым эталоном. После `TRUNCATE` тест проверяет возврат к SQL до перестройки.
4. Записать результат, включая число сравнений, маршруты и ограничение метода. Одна одноразовая PostgreSQL 18.7 по digest, без сети, без рабочих томов и портов, до 2 CPU и 1 ГиБ RAM. DuckDB 1.5.4 использует локальную память. Малый объём выбран для проверки поведения, в особенности NULL, пустых групп и транзакций. Скорость и потребление ресурсов не входят в эту проверку.
5. Следующий этап — изолированная сборка авторского артефакта по закреплённой версии с отдельным DuckDB capture fork и PostgreSQL 17 server headers. После сборки применить независимый оракул к поддерживаемым запросам, проверить накладные расходы записи, задержки p50/p95, CPU, память и I/O. Условия для полного пилота описаны в [предыдущем обзоре](../../reviews/jetstream/2026-11-14.md).

Текущий критерий прохождения — полное совпадение точных результатов, правильные маршруты, обнаружение устаревшего результата и сохранение старого снимка. Проверка относится к лабораторной реализации контракта.
