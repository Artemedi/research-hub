# REA — проверка метаданных управляемой сборки

## Условия

Нужны PowerShell 7, .NET SDK с установленными пакетами целевой платформы и Node 24 с поддержкой `--experimental-transform-types`. Прогон использовал .NET SDK 11.0.100 и Node 24.22.3. Скрипт проверяет чистоту отслеживаемых исходников REA и закреплённый коммит `92f332652d352e60b550567adf2399d83d8ebe78`. Сборка использует пустой список источников NuGet.

Из корня исследовательского репозитория выполните:

```powershell
./experiments/reverse-engineer-anything/run-managed-metadata.ps1 -Source <pinned-rea-checkout> [-Node <node-24-executable>]
```

## Сравнение

1. Скомпилировать два варианта [Fixture.cs](Fixture.cs) с одной и той же версией сборки. Во втором варианте добавить метод `Multiply`.
2. Получить эталон из тех же файлов через стандартные `PEReader` и `MetadataReader`. [MetadataOracle.cs](MetadataOracle.cs) читает файл потоком. Управляемые сборки с тестовыми методами не загружаются в рантайм и не исполняются.
3. Запустить оригинальные функции REA чтения PE и инвентаризации метаданных три раза на каждом варианте. Сверить имя модуля и MVID, имя и версию сборки, имена и версии ссылок, токены и абсолютные смещения этих записей, количество строк TypeDef и MethodDef. Ошибки парсера, отсутствующая запись и любое расхождение завершают прогон с ошибкой.
4. Проверить, что стандартный читатель показывает ровно один и два метода соответственно. Повторная сборка с тем же SDK должна дать прежние SHA-256 и JSON.

Отчёт появляется в стандартном выводе. Сообщения сборки идут в поток ошибок. Прогон ограничен маленькими синтетическими библиотеками и использует временный каталог.
