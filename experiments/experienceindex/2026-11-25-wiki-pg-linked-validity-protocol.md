# ExperienceIndex — проверка актуальности связанных документов Wiki_PG

1. Закрепить чистый checkout Wiki_PG на `d55721bb99bff25fae352341cfd630c048693d6b` и дату оценки 25.11.2026. Использовать штатную сборку локального SQLite и лексический поиск, с искусственными Markdown-документами во временном каталоге.
2. Сравнить три варианта. **A** — лексический поиск по исходному запросу. **B** — тот же поиск плюс один переход по относительной ссылке из найденного текста, с фиксированным термином для извлечения фрагмента на целевой странице. **C** — вариант B с проверкой `current_state_eligible` для обеих сторон.
3. До запуска задать девять сценариев и эталон. В одном актуальны оба документа. В семи хотя бы один документ не проходит проверку из-за срока, статуса, проверки человеком или изменения файла после индексации. Девятый сценарий указывает на посторонний актуальный документ из того же каталога, чтобы проверить ограничение условия C.
4. Повторить сборку и поиск на новом временном каталоге для каждого случая. Ожидать одинаковых результатов в двух повторах. Вариант C должен пропустить актуальную пару и отклонить все семь пар с нарушением актуальности. Девятый сценарий должен показать, можно ли ошибочно принять корректно индексированную, но нерелевантную цель.

Для запуска передать путь к закреплённому checkout в [скрипт прогона](wiki-pg-linked-validity.py). Из зависимостей нужны Python, SQLite с FTS5 и PyYAML из среды Wiki_PG. Сеть и модели для прогона не нужны. [Исходная статья, arXiv v1](https://arxiv.org/html/2610.10091v1) · [Предыдущая проверка ссылок](../../reviews/experienceindex/2026-11-07.md)
