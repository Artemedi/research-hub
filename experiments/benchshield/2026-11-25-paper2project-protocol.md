# BenchShield — протокол проверки сохранённых результатов Paper2Project

1. Закрепить исходники `dsh-paper2agent@c3bbe09bddf54b0efdcc0da1f17e1446dd35a4fd`. Проверять штатный отчёт и штатное хранилище на временной Linux-файловой системе. Рабочие пространства в проекте не используются.
2. Создать семь семейств из четырёх вариантов каждое. Каждое задание регистрирует искусственные материалы и план с единственной метрикой. Эталон рассчитывает сумму трёх целых чисел из исходного файла. Ожидаемые статусы и решения заданы до чтения отчёта.

| Семейство | Статус опыта | Решение отчёта |
| --- | --- | --- |
| Совпадение с эталоном | PASS | REPRODUCED_BENEFIT_UNPROVEN |
| Числовое расхождение | FAIL | EXPERIMENT_FAILED |
| Завершённая запись без обязательного объекта фактов | FAIL | EXPERIMENT_FAILED |
| Прерванная попытка | INTERRUPTED | EXPERIMENT_INCOMPLETE |
| Запуск заблокирован | BLOCKED | EXPERIMENT_BLOCKED |
| Старый формат сохранённых фактов | STALE | STALE_EVIDENCE |
| Только зарегистрированный план | NOT_RUN | EXPERIMENT_NOT_RUN |

3. Сравнить JSON-статус, решение и текст Markdown. Для завершённых числовых случаев дополнительно проверить количество сравнений и значения сравниваемых чисел. Критерий прохождения — 28/28 и два одинаковых агрегированных результата.
4. Разделить вывод о сравнении метрик и вывод о полноте доказательств. В [BenchShield, §4.5](https://arxiv.org/html/2609.11028v1#S4.SS5) исход задачи и уверенность в происхождении данных имеют разные вердикты. Отдельно отметить, какие из этих различий видны в Paper2Project и какие требуют дополнительного наблюдения.

Локальный тест создаёт маленькие данные в памяти и временных файлах. Агент, оценочный движок BenchShield и контейнеры не запускаются. Записи моделируют состояния исполнения. Отдельный инфраструктурный сбор событий остаётся дальнейшим шагом.
