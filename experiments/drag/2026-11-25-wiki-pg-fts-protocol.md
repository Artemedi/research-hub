# DRAG — разбиение составного запроса в Wiki_PG

1. Закрепить Wiki_PG на `d55721bb99bff25fae352341cfd630c048693d6b`. Собрать один временный индекс штатным сборщиком из искусственных отчётов для шести вымышленных хостов. Зафиксировать 30 запросов, по шесть каждого типа: один факт, два факта с разными портами, два факта среди лексических совпадений на другом порту, составной запрос без одного факта и запрос без единственного факта.
2. Сравнить три стратегии. Одиночный FTS передаёт все маркеры одним запросом. Раздельный FTS делает один запрос на каждую явно заданную пару «маркер и порт». Адаптивный FTS начинает с общей выдачи и повторно ищет только отсутствующие части составного запроса. Все используют штатный Python API `evidence_search.search` с `semantic=False` и `limit=3`, один индекс и одинаковые ограничения хоста и региона. Каждая стратегия может отдать максимум один фрагмент на часть запроса. Дубликаты одного фрагмента не увеличивают счётчик источников.
3. Проверять, совпадают ли маркер и номер порта. При отсутствии хотя бы одной части итог оставлять неполным. Эталон задаёт пути ожидаемых файлов при генерации корпуса. Сверять путь, хеш и диапазон строк по исходным байтам. Стратегии не получают эталонные пути.
4. Сохранить полные наборы на 18 положительных случаях, ошибочно полные наборы на 12 неполных, точность проверенных источников и число обращений к поиску. Положительным сигналом считать больше полных наборов против одиночного FTS, тот же набор результатов и меньше обращений относительно раздельного FTS, без ложного утверждения о полноте. Равная стоимость или ухудшение также фиксируются. Два запуска должны дать одинаковые агрегаты, индекс должен остаться неизменным.

Входы имеют явно размеченные части. Измеряется стоимость в вызовах FTS, а не CPU или задержка. Подход заимствует идею разных уровней поиска. В нём нет Avg-IDF, perplexity, плотного поиска и генератора DRAG. [Статья v1, §4.1](https://arxiv.org/html/2609.17709v1#S4.SS1) · [Предыдущий опыт](../../reviews/drag/2026-11-06-evidence-gate-ab.md)

После первого прогона добавлен отдельный диагностический контроль `single_default`. Он делает один запрос со штатным `limit=8`, сохраняя прежнюю проверку и лимит на итоговые фрагменты. Корпус, вопросы и три исходные ветки не менялись. Для всех веток отдельно считаются фрагменты, возвращённые поиском до проверки маркера и порта. Эти счётчики не показывают объём внутренней работы FTS.
