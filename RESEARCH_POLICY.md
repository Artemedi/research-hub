# Протокол исследовательского архива

## Источники и временное окно

Искать новые либо существенно обновлённые после последнего успешного обзора работы во всех технических областях, определяемых проектами из [project-registry](https://github.com/Artemedi/project-registry). Не ограничиваться DSH, агентами или ключевыми словами из прежнего расписания. Отделять первую публикацию, новую версию и дату обнаружения.

Для каждой работы фиксировать название, дату/версию, первоисточник (arXiv/DOI, авторский engineering blog, официальный исходный код), воспроизводимость результатов, ограничения и лицензию при необходимости.

**Полный текст обязателен.** Аннотация, пресс-релиз и snippet годятся только для screening. Анализ методологии, результатов и ограничений допускается после чтения полного доступного HTML/PDF/авторского текста. Иначе `FULL_TEXT_UNAVAILABLE`; не делать детальные научные выводы по abstract. Для engineering-реализаций читать код/тесты/официальную техническую документацию, а не маркетинговый анонс.

## Исследование → проекты

1. Начать с актуальной ветки и SHA `project-registry`. Рассматривать все карточки, включая проект коллеги, а не только один заранее выбранный target.
2. Для достойных работ выбирать shortlist из 1–3 наиболее подходящих проектов. Допускается отказ от всех проектов, если интеграция спекулятивна.
3. Для доступного source repo читать актуальные исходные файлы и тесты. Подтверждать место внедрения как `repository@SHA/path:line`; различать `VERIFIED`, `AUTHOR_STATED`, `HYPOTHESIS`, `UNKNOWN`.
4. Для проекта без доступного repo использовать предоставленный `SOURCE_BRIEF.md`, помечать `AUTHOR_STATED` и `NEEDS_SOURCE_CODE`. Нельзя выдумывать актуальный HEAD, namespace, контракт, тестовый baseline или существующий интеграционный seam.
5. Отделять наблюдаемые результаты первоисточника от предполагаемой выгоды в наших проектах. Описывать риски: безопасность, лицензия, стоимость, CPU/GPU/RAM/VRAM/IO, latency, надёжность и техдолг.
6. Предлагать минимальный offline A/B с baseline, повторениями, независимым oracle, критерием успеха и бюджетом. Отсутствие измерений — `BLOCKED: MEASUREMENT_MISSING`.

## Формат отчёта и история

Для каждого периода создавать `reports/YYYY-MM-DD-portfolio-research.md`:

- окно поиска и SHA каталога;
- новая работа: версии, исходные ссылки, метод/фактические результаты/ограничения;
- краткий отбор по портфелю и shortlist, подтверждение архитектурной связи или `NEEDS_EVIDENCE`;
- практическая ценность/сложность 1–10 с основаниями;
- наименьший измеримый эксперимент и возможные риски;
- 1–3 приоритета; исключения и дубликаты с причиной;
- если нет подходящих работ — `NO_SIGNIFICANT_NEW_MATERIAL` вместо наполнения шумом.

Перед записью проверять предыдущие отчёты и URL/DOI/arXiv, чтобы не дублировать неизменённые работы. При существенной новой версии/факте делать **новую датированную запись** со ссылкой на старую, не исправлять прошлое молча. Дополнять навигацию в корневом README.

Исторические копии DSH являются **архивом**, не новым научным review и не кросс-проектным approval. Воссозданные исторические дайджесты не доказывают, что полный текст каждого paper был прочитан: при повторном использовании надо перепроверить его.

## Полномочия

Не изменять исходники проектов, production и GitHub Issues автоматически. Допускаются только документальные записи в этом приватном архиве. Paper2Project — самостоятельный экспериментальный инструмент, необязательный для архивирования. Все внедрения проходят отдельный human gate.
