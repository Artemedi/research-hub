# Единая модель данных — v2

Нормализованы **83/83 карточек**. `catalog/entities.json` хранит идентичность источников, версии, обзоры и оценки применимости. Markdown сохраняет исходный аналитический текст. Генерируемые страницы исследований и проектов — представления одних данных, а не независимые списки.

[Сценарий](migration-runbook.md) · [Журнал](migration-progress.md) · [Итог переноса](migration-completion.md)

## Сущности

| Сущность | Обязательные данные |
| --- | --- |
| Study | `id`, `title`, `kind`, `card`, `primary_url`, `current_review_id`, `fit_coverage`, `card_body_sha256`, `linked_materials` |
| Version | `id`, `study_id`, `ref`, `url`; для неизвестного ref — `unknown_reason` |
| Review | `id`, `study_ids[]`, `version_ids[]`, `date`, `document`, `source_coverage`, `limitations`, `supersedes` |
| Experiment | `id`, `study_ids[]`, `review_id`, `environment`, `result`, `scope`, `limitations`, `artifacts[]` |
| Project | `id`, `title`, `registry_revision`, `registry_card_url` |
| Assessment | `id`, `study_id`, `project_id`, `review_id`, `date`, `decision`, `evidence`, `reason`, `limitations`, `next_test` либо объяснённый null, `supersedes`, provenance |
| Current assessment | Единственный `assessment_id` для пары `study_id`, `project_id` |
| Study relation | `id`, `from`, `to`, `type`, `reason`, `review_id` |

ID не зависит от партии миграции или имени папки. Один обзор может охватывать несколько работ, а отдельная оценка работы — ссылаться на её раздел внутри общего выпуска или на исходную аналитическую карточку. Научный обзор, ограниченная проверка кода и операционный follow-up могут сосуществовать: поздний запуск не заменяет автоматически ранний научный разбор.

## Отдельная исследовательская диспозиция

Актуальное ограниченное решение по исходному портфелю 83 работ хранится в
[датированном реестре доказательств](../data/results/research-portfolio/2026-11-09-closure-ledger.json).
Его статусы не эквивалентны полю source_coverage обзора, fit_coverage источника,
decision конкретной связи с проектом или разрешению реализации.

Генератор показывает исследовательскую диспозицию в catalog/studies/, читая
этот один реестр; повторная редактируемая копия решения в entities.json не нужна.
При отсутствии доказательств допускается OPEN_EVIDENCE_ADJUDICATION, а не
фиктивный NO_FIT или ACCEPT. Текущий итог: 81 терминальное решение,
2 открытые source-to-project оценки физического KV-cache. Исторические обзоры
и current_review_id сохраняют свои собственные scope/даты.

## Два типа происхождения оценки

**Полный JSON-импорт:** `source_matrix`, `project_revision`, `project_card_sha256`. Сверяются исходные decision/evidence/reason, hash карточки, вся совокупность project IDs, количество строк и соответствие обзору. Историческое имя `project_revision` здесь означает ревизию реестра из исходной матрицы, а не автоматически SHA исходников проекта. Подтверждённый code seam требует отдельного repo@SHA/path:line в обзоре.

**Документальная оценка:** `source_document`, `source_line`, `source_excerpt`, `source_decision`. Для неё `project_revision` и `project_card_sha256` равны null с `unknown_reason`: перенос текста не удостоверяет изучение project source. Decision — `DOCUMENTED_CANDIDATE`, `DOCUMENTED_NO_FIT` либо `DEFERRED`; оригинальная формулировка сохраняется отдельно.

Цитата должна точно совпадать с указанной строкой. Для таблиц проект должен находиться в целевой колонке, а не в примере, ограничении или сравнении. Если название проекта находится в заголовке раздела, `source_context` и `source_context_line` должны точно совпадать с ближайшим действующим заголовком. Ссылка на другую научную работу внутри строки не может стать основанием для текущего Study.

## Покрытие и актуальность

- `MIGRATED`: полностью перенесена исходная JSON-матрица; это не доказательство пользы всех её проектов.
- `PARTIAL`: извлечены явные документальные оценки; это не повторная оценка всего портфеля.
- `NO_DOCUMENTED_ASSESSMENT`: отдельная проектная оценка не установлена. Это не NO_FIT.
- Неизвестная применимость и явный `NO_CURRENT_TARGET` дополнительно сохраняются в проверяемом `fit_summary`, когда это прямо сказано в источнике.

`NORMALIZED` описывает формат карточек: legacy-список обязан быть пуст. Этот статус не означает научную верификацию, полный импорт всех экспериментов или готовность к production. Статус разбора источника, результат опыта, project fit и разрешение внедрения остаются разными характеристиками.

`supersedes` задаёт историю, явные current pointers — текущий выбор. Циклы и выбор уже заменённой оценки запрещены. По максимальной дате или имени файла актуальность не угадывается. Исторические обзоры помечаются `HISTORICAL_REVIEW_RECORDED`, а не выдаются за новое чтение.

## Текст и экспериментальные данные

`card_body_sha256` контролирует текст исходной карточки без добавленной навигационной ссылки и с нормализованными переводами строк. Изменение анализа требует осознанного обновления provenance и соблюдения правил датированных исправлений; генерация не переписывает этот hash автоматически.

`linked_materials` сохраняет локальные ссылки исходной карточки. Это ссылки, а не автоматически подтверждённое родство методов или собственный эксперимент. Полные прежние результаты остаются в исходных протоколах и raw JSON.

Отдельные Experiment records имеют общий envelope. `PASS` подтверждает только указанный scope. `OBSERVED` фиксирует наблюдение, включая воспроизведённые дубли, и не выдаёт дефект метода за успешный результат. Сам перенос не запускает эксперименты. В каталоге сейчас три таких записи; остальные измерения доступны через сохранённые протоколы и ссылки, без искусственного переописания их результатов.

Licences/third-party terms остаются в первичных карточках и обзорах; эта схема не является license audit.

## Наполнение

1. Найти существующий Study по первоисточнику. Не создавать новый источник ради новой версии, обзора или оценки проекта.
2. Добавить Version и Review с честными unknown, датами и ограничениями. Для code/article/disclosure различать тип проверки.
3. Добавлять project fit только с проверяемым основанием. Не извлекать FIT из любого упоминания проекта. Сохранять исторические оценки и явные current pointers.
4. Обновлять обе стороны каталога генерацией из одних assessments. Не редактировать страницы проектов вручную и не копировать приватные описания/код.
5. Выполнить `node scripts/build-catalog.mjs`, `node scripts/check.mjs`, `node --test scripts/check.test.mjs scripts/entity-model.test.mjs scripts/document-assessment.test.mjs`, `git diff --check`.

Проверки контролируют формат, связи, цитаты, provenance и сохранность текста. Они не доказывают истинность prose, доступность внешних сайтов или актуальную работоспособность проектов.
