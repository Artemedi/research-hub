# Сценарий миграции единого каталога

Исходная точка: `ff6ee776495f39b81121f0ec54f060fa85860b71`, пять нормализованных источников и 76 карточек в явном legacy-списке. Это миграция существующих выводов, не повторное научное исследование и не разрешение внедрения.

## Порядок выполнения

1. Зафиксировать HEAD, чистоту checkout и состав очередной партии. Сначала переносить небольшие группы с однозначным provenance.
2. Исполнитель читает карточки, обзоры и первичные локальные матрицы. Готовит отдельный фрагмент Study/Version/Review/Experiment. Не изменяет общий каталог, проверки и исходные результаты; не публикует изменения.
3. Проверяющий сверяет каждый URL, pin, дату, scope и выбранный текущий обзор с существующим материалом. Неизвестные версии сохраняются как unknown с причиной. Упоминания проекта не превращаются автоматически в FIT.
4. Проверяющий переносит полные исходные матрицы без переименования доказательных статусов. Сохраняет историю и явные current pointers. Если схема не выражает исходный факт, расширяет контракт с тестом, а не подгоняет факт под имеющийся enum.
5. Связи, для которых нет однозначного основания, остаются NOT_MIGRATED. Карточка может быть нормализована раньше её project-fit и experiment records; эти покрытия учитываются раздельно.
6. Добавить ссылку из исходной карточки, убрать только эту карточку из legacy-списка, сгенерировать обе стороны каталога.
7. Выполнить контроль содержимого, проверки и тесты. При ошибке не публиковать партию; исправить или оставить конкретную запись в очереди с объяснением.
8. Публиковать проверенную партию отдельным коммитом, сверять файлы с GitHub и завершение CI. В журнале фиксировать реальный охват, а не только число созданных страниц.

## Партии

| Партия | Состав | Основание выбора | Начальное состояние |
| --- | --- | --- | --- |
| 01 | Hyra 2.0, Vercel Agent Desktop | Доступны отдельные обзоры и полные JSON-матрицы; есть статья, source gate и ограниченный GUI-опыт | READY |
| 02 | DSH Superagent Prototype и остальные инженерные обзоры с JSON | Проверка отличающихся decision/evidence contracts до расширения импорта | PLANNED |
| 03 | Инженерные обзоры с project-fit в Markdown | Редакционная сверка точных строк, частичного покрытия и revision provenance | PLANNED |
| 04 | Статьи из портфельных выпусков и исторических сводок | Общие обзоры, секции документов, повторные оценки и обоснованный NO_FIT | PLANNED |
| 05 | Неоднозначные связи и неполные первоисточники | Явные unknown/неполнота; без искусственного повышения evidence | PLANNED |

Точные последующие партии формируются по проверенным входам, а не по желаемому количеству записей. В очереди остаются все ещё не перенесённые пути из `catalog/entities.json:legacy_studies`.

## Приёмка партии

- Каждый Study имеет собственную идентичность, первоисточник, версию/объяснённый unknown, обзор и ограничения.
- Один обзор может охватывать несколько источников; связи задаются ID, а не именем папки.
- Все перенесённые assessments совпадают с исходной матрицей. Полный импорт действительно содержит всё множество её project IDs; partial не называется полным.
- Current pointers не ссылаются на заменённые записи; история не удаляется и не сортируется догадкой по имени файла.
- Публичные страницы используют только разрешённые уже опубликованные сведения о проектах. Закрытые тексты не копируются.
- Исходные карточки меняются только добавлением навигации. Старые обзоры, результаты, ledger, архив и код экспериментов сохраняются.
- `node scripts/build-catalog.mjs`, `node scripts/check.mjs`, `node --test scripts/check.test.mjs scripts/entity-model.test.mjs` и `git diff --check` завершаются успешно.
- Негативные тесты отклоняют неподтверждённую связь, потерю части импорта, подмену project URL и повышение/подмену исходного evidence.

Проверки offline. Установка зависимостей, сетевые агенты, live desktop, databases, production и повторный запуск экспериментов не входят в этот сценарий.

## Роли

Подготовку однозначных фрагментов можно поручать более лёгкой модели. Решения о происхождении, актуальности, неоднозначной применимости и публикации остаются у проверяющего. Принятая исполнителем запись не считается проверенной автоматически.

Фактический прогресс фиксируется в [журнале миграции](migration-progress.md). Контракт данных — [единая модель](data-model.md).
